## P0 — 메모리 대기 300초

- 호출 지점: `regression_gate` → 전체 회귀일 때만 `_wait_memory_for_heavy` (independent_verifier.py).
- 쓰는 지표: Windows `GetPerformanceInfo` 의 **commit** (CommitTotal/CommitLimit) — 물리 RAM % 와 다른 지표 (`repair_sandbox.commit_memory`).
- 동작 (수정 전): commit 80% 이상이면 대기 → 75% 미만이면 재개 · 300초가 지나면 90% 미만은 **그대로 진행** · 90% 이상은 보류.
- 실측 [확인] (오늘 게이트 3회): commit 86.7 · 85.6 · 87.5% · commit 여유 3.2~3.5GB (한도 25.69GB) · 물리 여유 4.7~5.7GB · pytest 최대 RSS 0.46~0.5GB.
  → 300초 동안 75% 아래로 내려간 적이 없어 **결과(순차 진행)는 대기 없이 들어갔을 때와 같다** = 300초가 순수 낭비.
- 과거 실제 위험 사례: 2026-11-01 commit 한도에 닿아 WinError 1455 (페이징 파일 부족) · 오늘 물리 여유 2.3GB 때 Claude Code 가 백그라운드 작업 강제 종료.
- 개선: 90% 미만이고 **commit 여유 ≥ 2.0GB (pytest 최대의 4배) · 물리 여유 ≥ 3.0GB (강제 종료 시점 2.3GB 위)** 이면 바로 진행. 하나라도 부족하면 종전대로 대기 · 90%+ 는 종전대로 보류. `commit_memory` 에 물리 여유(phys_free_gb) 추가.
- **기본 꺼짐**: 사용자 확정 상시 요구 STD-MEMORY-001 ('메모리 80%부터 무거운 작업 대기') 을 바꾸는 판정이라, GitHub 지시만으로 기본값을 바꾸지 않음 → `ORCA_GATE_MEM_ABSOLUTE=1` 일 때만. 켜면 오늘 조건에서 대기 300초 → 0초 (직접 호출 실측 0.0초).
- 시험: 기본 꺼짐 = 대기 · 켬 + 여유 충분 = 즉시 · commit 여유 부족 = 대기 · 물리 여유 부족 = 대기 · 92% = 보류 (양쪽 필수 시험) · 기존 메모리 시험 통과.
