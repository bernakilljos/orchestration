## 3. 반드시 닫아야 하는 구체 항목
### A. 과거 System32 오염 원인과 재발 방지 (R370)
- 2026-04-08 생성 시각, 키트 첫 Git commit(2026-04-12), bash 기록(2026-05-11 이후) 이외의 가능한 실제 shell history/Windows 이벤트/작업 스케줄러/설치 로그/과거 백업·커밋까지 근거 있는 범위에서 조사한다. 없는 이력을 복원한 척하지 마라.
- 출력 리다이렉션 `> powershell`, System32가 CWD였던 호출, 상대경로/임시파일/작업 스크립트 경로 결함을 현재 활성 코드에서 추적; **확인된 결함 메커니즘**을 임시 격리 환경에서 수정 전 FAIL→수정 후 PASS로 증명. 실환경 System32 새 파일 생성 금지.
- 우리 프로세스가 생성하는 임시 파일의 소유권·task ID·경로·만료를 관리해 **소유 확정된 임시 파일만** 작업 완료/실패/재개 시 자동 정리. 다른 Agent 결과·미추적 사용자 파일·운영 DB/원장/감사·실행 중 파일은 절대 삭제하지 않는다. 링크/경합/파일 바뀜/접근 거부/부분 실패에서 오삭제 0 시험.
- 사용자 목표는 과거 주체를 마술처럼 특정하는 게 아니라 **실제로 동일 사고가 다시 발생하지 않게 막는 것**. 다만 과거 원인이 확정되지 않았다면 `unknown`과 예방 입증을 별개 필드로 기재.

### B. 관리자 실행기 실증 (R365/R369)
- 실제 구현 소스·시험 코드 SHA를 GitHub에 push하고 ACL/작업 경로/SYSTEM 실행기 인수 검증/링크·TOCTOU·임의 명령 실행 차단을 독립 검토 가능하게 하라.
- 기존 두 번 `rc=3`은 이미 삭제된 대상이라 자동 **삭제 실효성** 증명이 아님. System32에 시험파일 만들지 말고 별도 격리 영역에서 **실제 설치된 실행 경로의 제한된 안전한 승인 시험**을 설계하고, 새로운 관리자 작업을 임의 추가하거나 승인 범위를 몰래 확장하지 말 것. 현행 허용 범위만으로 검증 불가능하다면 그 제한을 보고하라.
- 재부팅 후 유지/사용자 세션 재시작 후 실행/동시 요청/작업 입력·출력 링크/변조 차단 등 기존 미검증을 가능한 범위에서 채워라. **작업을 강제로 재부팅하거나 OS 설정을 변경하는 위험 동작은 명시적 사용자 동의 없이는 수행하지 말라.** 재부팅 미실행은 명확히 별도 남겨라.

### C. 신뢰 가능한 완료 보고와 회귀 결과 (R367/R364/R366)
- `installed:false`인데 INSTALLED, `Test-Path=True`인데 DELETE_DONE, `RUNNING`인데 REGRESSION_PASS, `PENDING`인데 DEPLOYED/DONE으로 채점하는 경로를 기존 보고/상태 전환 코드에서 차단하는 시험을 만든다. 근거 없는 사용자 해석·가짜 100점 판정 금지.
- R364 D6/D7 반복 안내와 Hook 교착: 기존 설계의 의도된 3회 제한을 유지하면서 세션 경계·반복 원인 기록 후 중복 안내가 발생하는 조건을 재현·안전 수정. 구조 충돌 시 다른 기능을 깨뜨리지 않는 최소 패치.
- R363 스킵된 링크 시험: 격리 시험에서 권한 없는 Windows의 링크 생성 대안을 사용하거나, 가능한 CI 환경에서 확실히 실행. 미실행이면 SKIPPED로 남기고 차단·보존의 다른 검증을 추가; 임의 PASS 금지.
- 기존 2차 회귀의 프로세스/로그/exit code 결과부터 조회하고 PASS/FAIL을 확정, 남은 FAIL이 있으면 원인 수정 후 **필요한 범위만** 재검증. `head_commit:PENDING`/링크는 실제 push된 40자리 SHA를 확인한 다음 갱신.

## 4. 납품 및 종료 기준
- R370의 `.ai-collab/reports/R370.md`와 이 요청의 `.ai-collab/reports/R371.md`를 **실제 코드 push 후** GitHub main에 게시. 내용은 항목별 `증상 | 원인 분류 | 수정 파일/줄 | 수정 전 결과 | 수정 후 결과 | 운영 실증 | 잔여 위험 | SHA` 표.
- `HISTORICAL_UNPROVABLE`이나 승인·플랫폼 제약이 남으면 단순 이름만 나열하지 말고 조사 범위와 **현재 예방·탐지·복구가 확실히 검증됐는지** 증명. 이를 역사적 원인 완전 규명이나 전체 PASS로 포장하지 않는다.
- 미검증 사항이 없어졌다고 거짓 보고하지 않는다. 위험이 낮아지고 검증된 항목만 닫으며, 해소 가능한 미검증은 실행 가능한 다음 단계까지 계속 처리.
- 실제 구현 커밋을 push하고 원격 SHA 확인, 사용자에게 **완료된 것/남은 것/그 이유**를 3~5문장으로 먼저 보고. ChatGPT가 독립적으로 `.ai-collab/reviews/R371.md`를 검토할 증거를 제공한다.
- 기존 보고서 중 시각이 다른 설치 상태·삭제 상태는 과거 이력 보존 + 현재 상태 분리로 정정. 감사 기록·증거는 삭제하지 않는다.

**이 지시의 성공 기준은 UNKNOWN을 전부 PASS로 바꾸는 게 아니라, 해결 가능한 항목은 직접 해결·증명하고 불가능한 과거 사실은 정직하게 구분하면서 현재와 미래의 위험을 실제로 제거하는 것이다.**
