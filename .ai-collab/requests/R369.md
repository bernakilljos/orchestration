# R369 — 지금 직접 삭제 + 최초 UAC 승인 후 승인된 관리자 작업 자동 처리의 실제 설치·검증

## 사용자 최신 지시 (반드시 먼저 답할 것)
사용자: "이거 하면 다음에는 알아서 지우는 거야? 하면 해주고, 아니면 알아서 지워."

**Claude CLI 첫 답변은 다음 사실을 기준으로 예/아니오부터 시작한다.**
- 관리자 PowerShell에서 제시한 `Remove-Item` 한 줄을 사용자가 실행하면 **이번 대상 파일만 삭제되는 것이고, 향후 삭제 자동화가 설치되지는 않는다.** "아니요. 그 한 줄만 실행하면 이번 파일만 삭제됩니다. 다음번 자동 처리는 별도 관리자 실행기 설치와 사전 승인 범위 설정이 필요합니다."
- 현행 `elevated-task.ps1`의 앞선 실측 `installed:false`이면 **관리자 실행기는 구현·테스트와 관계없이 아직 설치되지 않은 상태**다. 최신 실측이 달라졌다면 변경 시각과 출력을 근거로 보고.
- 향후 **모든 파일을 무조건 삭제**하는 만능 권한은 부여할 수 없고, 해서는 안 된다. 최초 관리자 승인 이후 **사용자가 사전에 지정·승인한 경로와 작업 종류**에 대해서만 반복 UAC 없이 실행 가능한 구조를 구현한다.
- 이전처럼 장문의 R364 보고서, R354 조사, 긴 회귀 게이트를 앞세워 질문에 답하지 않는 행동을 즉시 중단한다.

## P0 — 바로 수행할 순서
1. **첫 응답(질문 즉답) 후 실제 작업 진행.** 사용자에게 또 다시 관리자 PowerShell 명령을 복사해 직접 삭제하라고만 말한 뒤 종료하는 것은 실패다.
2. 현재 작업 파일, 회귀 게이트 PID, Windows 권한, `Test-Path 'C:\Windows\System32\powershell'`, 설치 상태(`elevated-task.ps1 -Action Status` 등)를 최소 한 차례 실측하고 기록한다. 회귀 게이트는 중복 실행하지 않는다.
3. 사용자 명시 지시의 안전한 대상이 확장자 없는 0바이트 일반 파일인지, 정상 `powershell.exe`와 무관한지, 리파스 포인트나 보호 Windows 파일이 아닌지 재확인한다.
4. **Claude CLI가 직접 정상 Windows UAC 승인 흐름을 시작**할 수 있는 실제 경로를 우선 선택한다. 현재 작업 중인 설치·요청 스크립트를 재사용하고 관리자 설치기/실행기 호출이 허용되면 Windows 공식 승격으로 '예/아니오' UI를 표시하라. 사용자가 직접 '예'를 선택하게 한다. 승인되지 않은 작업은 실행하지 않는다.
5. 이번 조건부 파일 삭제와 **향후 허용 범위 내 반복 자동 처리를 위한 등록된 관리자 작업 설치**를 별개 결과로 관리한다. 필요한 권한과 승인 범위가 동일한 경우 초기 1회 사용자 동의하에 연결할 수 있는지 검증하되, 임의 관리자 셸·전역 UAC 끄기·내부 승인 게이트/DB 위조·보안 우회 금지.
6. OS 승격 호출이 내부 Hook/승인 게이트에서 차단되면 실제 승인 방법이 지원되는지 확인하고 **검증된 사용자 동작 단 하나**를 제시. 기존 `appr-713617e80d83`이 실제 유효하지 않으면 유효한 척 안내하지 않는다.
7. 승인 이후 파일 조건부 삭제를 실행, `Test-Path=False`, 정상 Windows PowerShell 시작, 이전 앱 선택 창 미재현을 확인하라. 삭제에 실패했다면 `BLOCKED`로 유지한다.
8. 관리자 예약 작업 설치는 `installed:true`뿐 아니라 등록 작업 동작, 일반 CLI 요청 성공, 허용 범위 밖 요청 차단, 일반 사용자의 높은 권한 코드/설정 변조 차단을 **실제 운영 환경**에서 확인하라. 검증되지 않은 재부팅 지속성 등은 `NOT_VERIFIED`로 둔다.
9. 설치된 관리자 실행기는 명령 문자열을 그대로 상승 권한으로 실행하는 범용 통로가 되어서는 안 된다. 허용 작업 유형·대상 경로·인수·호출 ACL·스크립트 무결성을 검증하고 실시간 로그를 남긴다. 사용자 승인 범위 밖의 삭제는 거절한다.

## 2026-11-23 P0 검증 지시 — "앞으로 나한테 안 물어보는가"를 실제 증거로 판정

### 사용자 첨부 최신 로그의 중요 사실
- 사용자는 `/approve appr-713617e80d83`을 입력했으나, 화면에는 `Queued · ctrl+enter to send now`가 표시되었다. **입력한 것과 공식 승인 완료는 다르다.** 이 화면만으로 승인 상태를 APPROVED라고 기록하지 말 것.
- 설치 스크립트에서 SYSTEM principal로 수정한 것은 **코드 변경**이다. 실제 설치 성공이나 보안 안전성을 의미하지 않는다.
- Claude가 "설치만 하면 그 다음부터 다른 관리자 작업도 알아서 하겠다"고 답했으나, 제공 로그에서 당시 허용된 작업은 `remove-shadow-command` 한 종류뿐이다. **'다른 파일이든 뭐든' 무조건 자동 처리된다는 약속은 검증되지 않았고 기술적으로도 승인 범위가 한정된다.**
- GitHub main에는 이 시점까지 R365·R366·R368·R369 완료 보고가 게시된 것을 확인하지 못했다. 사용자 로컬의 `head_commit:PENDING` 보고서 작성과 GitHub push 완료는 구분한다.

### Claude CLI가 지금 반드시 할 일 (P0)
1. 다른 작업에 앞서 사용자 질문에 한 문장으로 답한다: "아직 자동 삭제가 설치·검증됐다는 증거는 없습니다. 승인된 작업 범위에 한해 최초 설치 후 반복 확인 없이 처리할 수 있도록 검증하겠습니다." 최신 Windows 실측이 있다면 그 결과에 맞춰 정정.
2. 현행 승인 DB에서 기존 ID의 상태를 읽고 **사용자가 전송 대기 중 입력한 /approve를 실제로 소비했는지** 확인. Queued 상태만으로 승인됐다고 간주하거나 DB를 수동 변경하지 않는다. 공식 승인 명령이 실제 구현되어 있는지 확인.
3. 현재 Windows 실환경에서 관리자 작업의 `Status`를 실행하고 등록된 Task 이름/Principal/TaskPath/실제 실행 가능 상태를 조회한다. `installed:false`면 미설치로 보고한다.
4. 설치가 필요한 경우 Claude CLI가 정식 설치/UAC 창을 직접 개시할 수 있는지 확인하고 시도한다. 사용자가 '예'를 선택할 실제 UI가 나타나야 하며, 확인 전에는 절대 설치 완료 주장 금지. OS 정책상 사용자 직접 실행만 가능하면 원인과 **최소한의 검증된 한 가지 사용자 동작**을 제시한다.
5. 설치 후 **일반 권한 Claude CLI에서 사전 승인된 작업을 직접 호출**하여 (a) 허용 작업 정상 수행 (b) 허용되지 않은 명령/경로 거부 (c) 고권한 파일·allowlist 변조 거부 (d) 로그/종료 코드 확인 (e) 실제 사후조건 확인을 격리 테스트 대상으로 수행한다. System32에는 시험용 새 파일 생성 금지.
6. 이번 사용자 승인 범위에 정확히 포함된 문제 파일에 한해 실제 조건부 제거 및 `Test-Path=False` 검증. 정상 `powershell.exe` 유지와 '앱 선택' 현상 해소도 별도 확인한다.
7. 이후 동일한 *이미 승인된* 작업을 반복 요청할 때 UAC·수동 PowerShell·재승인을 요구하지 않고 실행되는지 **두 번째 호출**로 확인한다. 첫 호출 성공만으로 '앞으로 자동' 판정 금지.
8. 다른 파일 경로와 다른 종류의 관리자 작업이 필요한 경우, 기존 작업의 허용 범위를 몰래 확대하지 말고 명시적 사용자 승인으로 신규 등록·검증. 일반 권한에서 수정 가능한 스크립트/allowlist를 SYSTEM이 실행하는 설계면 P0 취약점이므로 운영 적용 중단·수정.
9. 진행 중 회귀 게이트는 중복 실행하지 말고 기존 실행 결과를 그대로 활용. R354와 무관한 조사·보고를 앞세우지 마라.
