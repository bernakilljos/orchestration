# R370 — 삭제 성공 후 System32 오염 원인 추적 및 재발 방지

## 현재 사실
사용자 제공 Claude CLI 로그: 2026-11-23 17:53:19 KST `C:\Windows\System32\powershell`의 `Test-Path=False`, 정상 powershell.exe 이름 호출 성공. 사용자 `/approve appr-713617e80d83`가 처리된 뒤 삭제된 것으로 보고됨. **같은 파일을 재삭제하거나 기존 승인을 반복 요청하지 마라.** 위 사실은 사용자 제공 실행 로그에 근거하며 원격 GitHub에 반영됐다는 뜻은 아니다.

## 사용자 최우선 질문
**"왜 쓸데없이 System32에 만들었나? 실제 누가, 어떤 명령이나 코드가 만들었나?"**

첫 문장에서 원인이 확인됐으면 구체적 원인, 아니면 "아직 생성 원인은 확인되지 않았습니다"라고 답하라. 2026-04-08 파일 생성, 출력 리다이렉션 잔재는 기존 `docs/FINAL_AUDIT_PLAN_2026-11-03.md`의 **추정**이지 확정 원인이 아니다. 근거 없이 Claude나 사용자가 만들었다고 단정하지 말 것.

## 구현 및 검증 지시
1. 기존 파일이 삭제되어 메타데이터 일부가 사라졌으므로 **기존 보존 로그/감사 이력/쉘 명령 이력/당시 코드와 Git 이력**에서 해당 파일 생성 경로를 추적하라. 로그가 없으면 UNKNOWN으로 끝내고 허구의 범인·명령·정확한 원인을 만들지 마라. 운영 로그, DB, 원장은 삭제하지 마라.
2. 특히 System32가 잘못된 작업 디렉터리가 된 실행, `> powershell` 등 출력 리다이렉션, 상대경로 생성, PowerShell/Git Bash/Hook/Agent 호출과 사용자 정의 스크립트의 현재 작업 디렉터리 및 경로 해석을 근거 중심으로 확인한다. 실제 관련 호출의 파일/함수/라인을 기록.
3. **원인을 특정할 경우** 해당 정본 코드의 작업 디렉터리와 출력 경로를 바로잡고 오염 방지 검증을 추가한다. 특정 못하더라도 위험한 상대 출력 경로가 System32에 향하지 않게 하는 최소한의 예방 조치를 기존 구조에 적용할 수 있는지 검토한다. 정상 Windows 실행·시스템 업데이트를 광범위하게 차단하지 않는다.
4. 모든 재현은 격리 임시 폴더에서 수행한다. System32에 테스트 파일을 새로 만들지 않는다. 수정 전 FAIL, 수정 후 PASS와 정상 PowerShell 실행 회귀를 기록.
5. R363 삭제 완료를 유지하되, **관리자 실행기 설치 여부는 별도** 확인한다. 설치가 실제 검증되지 않았으면 향후 모든 파일 삭제가 자동이라고 주장하지 마라. 사용자가 이미 처리한 승인 요청은 반복 소비하지 않는다.
6. 기존 회귀 게이트·진행 중 워커를 존중하고 중복 장시간 회귀를 시작하지 않는다. 필요 시 표적 테스트만 추가한다.
7. `.ai-collab/reports/R370.md`에 '생성 주체 확정/추정/UNKNOWN', 증거, 수정 파일, 테스트, 실제 Git commit/push, 이번 문제의 사후 검증 및 남은 위험을 구분해 게시한다. R363 보고서의 이전 BLOCKED는 과거 이력으로 남기고 최신 삭제 성공을 반영한다.
8. 사용자 질문에 답하기 전 R354/R364 등 무관한 보고서 작성이나 Agent 작업에 착수하지 마라. 사용자가 원하는 건 왜 이런 사고가 발생했는지와 다시 생기지 않도록 실제로 조치했는지다.

## 완료 기준
- 실제 원인이 확인되면 정확한 코드와 재현 증거 + 소스 수정 + 재발 방지 테스트.
- 확인되지 않으면 UNKNOWN과 조사한 근거, 검증된 예방 조치만 보고.
- 사용자 질문에 즉답. 구현·테스트·배포·운영 결과를 절대 혼동하지 말 것.


## 2026-11-23 최신 사용자 지시 — 원인 증명 + 불필요 파일 생성 예방 + 안전 자동 정리 (P0)

사용자 원문: **"원인도 찾고 증명해서 생기지 않게 해.... 쓸데없는 파일들 생기지않게 생기면 지워"**

### 1. 원인 조사와 '증명' 구분
- 이미 삭제된 System32 파일의 과거 생성 주체는 당시 감사/실행 이력과 코드로만 확정할 수 있다. 2026-04-08 생성과 리다이렉션 잔재라는 가설은 **증거가 없으면 UNKNOWN**이다.
- 당시 호출된 프로세스·부모 프로세스·작업 디렉터리·명령 문자열·표준출력/오류 리다이렉션·파일 생성/수정 시각, 관련 Git 커밋을 가능한 기록에서 교차 검증하라. OS 로그가 없으면 소급 증명 불가라고 명확히 밝혀라.
- 재현 가능한 **결함 메커니즘**과 **실제 과거 사건의 범인**은 다르다. 격리 임시 디렉터리에서 실패 명령을 재현해도 과거 사건의 생성 주체까지 입증됐다고 보고하지 마라.
- 발견한 원인 후보는 `confirmed/likely/unknown`과 증거 출처·라인·명령·출력을 분리하라. 추측을 확정으로 승격 금지.

### 2. 예방할 '불필요 파일'의 정확한 범주
- 사용자/운영/프로젝트의 임의 파일을 쓰레기라고 추정하여 삭제하지 마라. **정본 소스, 사용자 문서, DB/원장/로그/감사기록, Git 미추적 작업물, 실행 중인 다른 에이전트 산출물, 시스템 파일**은 보존 대상이다.
- 자동 정리 허용 범위는 **오케스트레이션이 직접 생성했고 소유권·경로·작업 ID·생성 규칙·유효기간 또는 작업 완료 여부가 검증된 임시 파일/중간 캐시/실패 실행 잔여물**로 좁힌다.
- `System32`, Windows, Program Files, 사용자 홈/다운로드, 임의 프로젝트 루트 등에서 패턴만 보고 재귀 삭제하는 동작 금지. 위와 같은 보호 영역의 미확인 파일은 탐지·격리 검토 대상으로만 분류. 정식 승인 대상은 기존 정책 유지.

### 3. 생성 전에 차단하는 구조적 개선
1. Bash/PowerShell/Python/Agent/Hook/예약작업에서 새 임시 산출물·리다이렉션 대상·작업 디렉터리 결정 경로를 조사해 실제 문제 경로만 최소 수정하라.
2. 작업별 전용 임시 디렉터리(명확한 루트·작업 ID·소유권)를 사용하고, 상대 출력 경로가 보호 시스템 디렉터리로 해석되는 실행은 실패 처리하라. 절대경로·부모 디렉터리·리파스 포인트를 검사하라.
3. 정상적인 시스템·외부 도구 작업은 맹목적으로 막지 않는다. 사용자 지정 출력 경로도 일괄 무시하지 않는다.
4. 기존 Hook/runner/cleanup 기능을 먼저 재사용하여 새 상주 감시 프로그램, 중복 스케줄러·자율 삭제 에이전트를 만들지 마라.

### 4. 생겼을 때의 안전 자동 정리 폐루프
1. 임시 파일 생성 시 작업 메타데이터(`task_id`, 절대 경로, 생성 주체/목적, 생성시각, 만료/보존 정책, 소유권, 작업 실행 상태)를 가능한 기존 로그/원장에 연계한다. 비밀값이나 개인정보는 남기지 않는다.
2. 작업 정상 완료/실패/중단 시 `finally` 또는 기존 실행 라이프사이클의 cleanup에서 직접 소유한 임시 잔여물만 삭제한다. 종료 뒤 남은 잔여물은 재개 시 **기존 기능으로** 유효기간·소유권·작업 비활성 여부 검증 후 처리하라.
3. 삭제 전에 `dry-run` 대상으로 예상 목록과 근거를 먼저 검증하고, 단위·장애 시험을 통해 안전성이 입증된 **사전 승인된 임시 영역**만 자동 삭제 허용한다. 알 수 없는 파일·다른 작업의 파일은 보존하고 간단히 보고한다.
4. 파일이 열린 상태/동시 작업 중/경로가 바뀐 상태/심볼릭 링크·junction/ACL 거부/삭제 실패/재부팅 후 재개 사례에서 **오삭제 0건**을 시험하라. 삭제 실패 시 재시도 한도를 지키고 상태 기록. 권한 우회 금지.
5. 운영 폴더에서 무차별 `git clean -fdx`, `Remove-Item -Recurse -Force` 등을 자동 실행하지 마라. 명시적으로 소유하고 격리된 캐시 외에는 정리 범위를 확대하지 않는다.

### 5. 필수 증거와 수용 기준 (100점 실증)
- **원인**: 과거 생성 경위 확정 여부(UNKNOWN 허용), 확인된 결함 메커니즘, 관련 파일/라인/재현 명령.
- **생성 예방**: 동일 입력에 대한 수정 전 실패→수정 후 보호 동작 PASS; 실제 시스템 경로에 시험파일 생성 금지.
- **자동 정리**: 자기 소유 임시파일 자동 제거 PASS, 정상 파일/미추적 사용자 파일/다른 세션 산출물 보존 PASS, 링크/경합/잠금/거절 시 안전 유지 PASS.
- **운영 실증**: 관리자 자동 실행기 `installed:true`인지 별도 확인하고 미확인이면 미완료로 표기. 이번 R363 삭제는 17:53:19 `Test-Path=False`로 확인된 과거 성공 사례이므로 다시 삭제/승인 요청하지 않는다.
- **비용/개발 부담**: 기존 진행 중인 회귀 게이트를 재시작하지 않고 표적 테스트 → 필요한 범위만 확장. Cleanup 자체가 더 큰 CPU/메모리/토큰 부담이나 상주 프로세스 증가를 만들면 실패.
- 결과는 `.ai-collab/reports/R370.md`에 **원인/예방/자동정리/보호 테스트/운영 적용/미확인 항목**으로 분리, 실제 코드 수정 커밋과 push 후 ChatGPT 독립 검토가 가능하도록 링크를 남긴다. 스크립트 파일이나 테스트만 만든 것을 자동 정리 운영 성공이라고 보고하지 마라.

**최종 목표: 불필요한 파일을 만들지 않는 것이 1순위, 우리 시스템이 실제로 만든 안전하게 식별된 임시 잔여물만 자동 정리하는 것이 2순위다. 시스템·사용자·프로젝트 데이터는 절대 추측으로 삭제하지 않는다.**
