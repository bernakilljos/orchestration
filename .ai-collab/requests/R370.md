# R370 — 삭제 성공 후 System32 오염 원인 추적 및 재발 방지

## 현재 사실
사용자 제공 Claude CLI 로그: 2026-11-23 17:53:19 KST `C:\Windows\System32\powershell`의 `Test-Path=False`, 정상 powershell.exe 이름 호출 성공. 사용자 `/approve appr-713617e80d83`가 처리된 뒤 삭제된 것으로 보고됨. **같은 파일을 재삭제하거나 기존 승인을 반복 요청하지 마라.** 위 사실은 사용자 제공 실행 로그에 근거하며 원격 GitHub에 반영됐다는 뜻은 아니다.

## 사용자 최우선 질문
**"왜 쓸데없이 System32에 만들었나? 실제 누가, 어떤 명령이나 코드가 만들었나?"**

첫 문장에서 원인이 확인됐으면 구체적 원인, 아니면 "아직 생성 원인은 확인되지 않았습니다"라고 답하라. 2026-04-08 파일 생성, 출력 리다이렉션 잔재는 기존 `docs/FINAL_AUDIT_PLAN_2026-11-03.md`의 **추정**이지 확정 원인이 아니다. 근거 없이 Claude나 사용자가 만들었다고 단정하지 말 것.

## 구현 및 검증 지시
1. 기존 파일이 삭제되어 메타데이터 일부가 사라졌으므로 **기존 보존 로그/감사 이력/쉘 명령 이력/당시 코드와 Git 이력**에서 해당 파일 생성 경로를 추적하라. 로그가 없으면 UNKNOWN으로 끝내고 허구의 범인·명령·정확한 원인을 만들지 마라. 운영 로그, DB, 원장은 삭제하지 마라.
2. 특히 System32가 잘못된 작업 디렉터리가 된 실행, `> powershell` 등 출력 리다이렉션, 상대경로 생성, PowerShell/Git Bash/Hook/Agent 호출과 사용자 정의 스크립트의 현재 작업 디렉터리 및 경로 해석을 근거 중심으로 확인한다. 실제 관련 호출의 파일/함수/라인을 기록.
3. **원인을 특정할 경우** 해당 정본 코드의 작업 디렉터리와 출력 경로를 바로잡고 오염 방지 검증을 추가한다. 특정 못하더라도 위험한 상대 출력 경로가 System32에 향하지 않게 하는 최소한의 예방 조치를 기존 구조에 적용할 수 있는지 검토한다. 정상 Windows 실행·시스템 업데이트를 광범위하게 차단하지 않는다.
4. 모든 재현은 격리 임시 폴더에서 수행한다. System32에 테스트 파일을 새로 만들지 않는다. 수정 전 FAIL, 수정 후 PASS와 정상 PowerShell 실행 회귀를 기록.
5. R363 삭제 완료를 유지하되, **관리자 실행기 설치 여부는 별도** 확인한다. 설치가 실제 검증되지 않았으면 향후 모든 파일 삭제가 자동이라고 주장하지 마라. 사용자가 이미 처리한 승인 요청은 반복 소비하지 않는다.
6. 기존 회귀 게이트·진행 중 워커를 존중하고 중복 장시간 회귀를 시작하지 않는다. 필요 시 표적 테스트만 추가한다.
7. `.ai-collab/reports/R370.md`에 '생성 주체 확정/추정/UNKNOWN', 증거, 수정 파일, 테스트, 실제 Git commit/push, 이번 문제의 사후 검증 및 남은 위험을 구분해 게시한다. R363 보고서의 이전 BLOCKED는 과거 이력으로 남기고 최신 삭제 성공을 반영한다.
8. 사용자 질문에 답하기 전 R354/R364 등 무관한 보고서 작성이나 Agent 작업에 착수하지 마라. 사용자가 원하는 건 왜 이런 사고가 발생했는지와 다시 생기지 않도록 실제로 조치했는지다.

## 완료 기준
- 실제 원인이 확인되면 정확한 코드와 재현 증거 + 소스 수정 + 재발 방지 테스트.
- 확인되지 않으면 UNKNOWN과 조사한 근거, 검증된 예방 조치만 보고.
- 사용자 질문에 즉답. 구현·테스트·배포·운영 결과를 절대 혼동하지 말 것.
