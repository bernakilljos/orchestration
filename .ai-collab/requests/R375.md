# R375 — 하드코딩 중심 대응 제거: 동적 사용자 의도·작업·승인·검증 폐루프

## 사용자 최신 요구 (최상위)
"어제랑 오늘이랑 이것 봐 하드코딩이잖아. 난 동적으로 좋아한다고."
"다른 것도 찾아서 내 말 좀 지키라고 좀 해."

**사용자는 특정 오류마다 ID, 승인 번호, 디렉터리, 서버 이름, 예외 패턴, 테스트 명령을 수동 추가하는 시스템을 원하지 않는다.** 한 번 지시한 목표를 시스템이 이해하고, 실행 가능한 작업으로 분해하며, 위험과 증거를 동적으로 판정해 완료할 때까지 실행·검증·재개하는 *1인용* 오케스트레이션을 원한다. 단순하게 규칙 몇 줄 추가하는 것으로 완료 선언 금지.

## 관측과 문제 정의
- 최근 R363~R374 대응에서 특정 대상 System32 파일, 두 개 복사본 경로, 승인 ID, MCP 서버 5개 이름, R371 미완료 코드 목록을 지시문에 개별 열거했다. 이는 **사건을 특정한 진단 및 테스트 입력**으로는 필요하지만 **실행 정책과 로직에 그대로 박히면 하드코딩**이다.
- 실제 소스의 `approval-gate.py`는 위험 명령 정규식 목록, `elevated-task.ps1`은 `remove-shadow-command`라는 고정된 단일 관리자 작업만 허용, `ai-collab-report.py`와 `auto-save-next-actions.py`는 일부 고정 명령/블록·필터에 의존한다. 모두 무조건 잘못된 것은 아니다. **보안상 고정해야 하는 정책 경계**와 **확장 가능해야 하는 동작·대상·워크플로우**를 구분해 실제 결함을 찾아라.
- R372/R373 보고에서 세션 시작 자동 복구와 MCP 연결은 코드 변경 뒤 다음 실제 세션 검증이 남아 있다. R374 폴더 삭제는 요청만 게시되었고 실제 완료 보고는 미게시다.
- 최신 기준 GitHub main `08acd49e728c5a142738e2c6034e530ae7c5b507`. 이후 새 코드가 올라오면 최신 SHA로 재검토하라.

## 1. 동적화 원칙 — 정책은 명시적, 실행 대상은 데이터로
1. **인수/경로/요청 ID/서버 명칭을 코드에 박아서 작업 종류를 늘리는 방식 금지.** Request/Goal/Approval/Execution/Verification/Report를 구조화된 유형 및 메타데이터로 모델링하고, 새 요청은 기존 실행기에 동적으로 바인딩하라.
2. 정책 엔진은 **데이터 기반**으로 구성할 수 있으나 보안 불변식(사용자 단회 승인, 권한 범위 제한, 운영/사용자 데이터 보존, UAC 비우회, 대상 경로의 신원 검증)은 완화 금지. '동적'은 '모든 명령 자동 허용'이 아니다.
3. 실행기/Hook/CLI의 작업 식별자는 텍스트 명령이나 바뀌기 쉬운 문자열이 아니라 `operation_id + requested_intent + resolved_scope + policy_version + evidence_hash` 같은 정규화된 계약으로 연계하라. 최초 승인된 **정확한 작업 범위**와 동일한 후속 단계는 중복 승인 없이 재개하되, 범위가 변경되면 재평가/재승인.
4. 여러 작업을 한 번에 수행할 때 각 작업의 선행조건·사후조건을 선언하고 의존성 그래프/DAG에서 진행률을 동적으로 판단하라. '활성 워커가 0'과 '할 일 없음'을 혼동하지 않는 구조.
5. 템플릿/레지스트리를 한곳에서 관리해 사용자 지시·도구 종류·대상·검증기를 플러그형으로 결합. 새 폴더나 새 MCP 서버 이름 때문에 Python 소스의 조건문을 또 추가하지 않도록 한다.
6. 런타임 보안 통제의 정책 구성은 안전한 관리자/사용자 승인 흐름에서만 갱신. 일반 권한 사용자가 SYSTEM 실행 코드나 allowlist를 조작해 권한 상승할 수 없어야 하며, 만능 관리자 shell·무제한 삭제·임의 스크립트 실행 통로는 금지.
7. 규칙 기반 탐지의 허점을 임의 정규식 1개 추가로 계속 해결하지 말고 가능한 범위에서 명령의 **실행 계획/AST·정규화된 경로·작업 디렉터리·변수 확장·실제 파일 시스템 속성**을 분석하는 계층으로 전환. 파싱/검증 불확실한 파괴 작업은 실패 안전(fail closed). 다만 OS 외부 셸 전체에 대해 완전한 사전 차단이 가능하다는 과장 금지.

## 2. 전수 조사 — 사용자 지시를 놓치는 공통 결함을 찾아라
코드와 실제 로그에서 다음 경로의 하드코딩/누락/불일치를 표로 기록하라.
- 자연어 사용자 지시 → 의도(요구 결과/선행조건/금지조건) → 작업 계획 → 승인 → 실행 → 검증 → 완료 보고 → 미완료 재개.
- GitHub requests/reviews/보고서 수신 → state/ledger/next-actions → SessionStart/Stop/Supervisor → 실제 작업 착수.
- 파일 정리: 고정 이름 임시 파일이 아닌 **생성 주체/manifest/수명** 기반 자기 소유 산출물 정리. 임의 사용자 파일은 추측으로 삭제 금지.
- 복사본 삭제: 특정 두 폴더 경로의 직접 허용 예외 대신, 대상별 소스-원격 일치와 로컬-only 데이터·링크·경합 등 동적 검증 + 정확한 승인 범위.
- MCP 연결: 특정 서버 5개 문자열 조건 대신 실제 등록 MCP 목록 열거 → 개별 건강검진/재시도/우선순위·완전 실패 시 감소 모드.
- 검증: 특정 R번호마다 보고 PASS 하드코딩하지 않고 목표별 사후조건 증거와 실행 시점·SHA·운영환경을 동적으로 결합.
- 사용자 직접 지시보다 R354/과거 게이트 등 관련 없는 작업을 앞세우는 우선순위·응답성 결함.
- 요청 ID/폴더/명령 문자 변경마다 재승인이 새로 생기는 상황, 보고만 작성하고 실제 실행하지 않는 상황, 세션 재시작 후 review/next-action을 놓치는 상황.

단, 고정된 이벤트 타입·검증된 기본 정책·표준 exit code·보안 허용 경계 같은 **의도적인 상수는 유지해도 된다**. 무조건 모든 정규식을 지우거나 거대한 프레임워크로 전면 교체하지 마라.

## 3. P0 구현 순서 — 작은 수직 슬라이스를 끝까지
1. 우선 **실제 R374 승인/삭제 상태를 확인하고 사용자 결과부터 처리**. 기존 유효 승인 ID를 읽어 승인 작업을 끝까지 실행하고, 범위 밖 사용자 데이터는 보존. 폴더가 이미 없으면 그 사실 확인. 사용자가 승인하지 않았다면 임의 승인/삭제 금지.
2. 기존 Hook/approval gate/ledger/runner/own-cleanup/Supervisor를 조사해 재사용할 **공통 Operation Contract**를 최소 설계한다: `kind`, `scope`, `intent`, `preconditions`, `postconditions`, `policy`, `approval_ref`, `status`, `evidence`, `resume_token`. 민감 정보는 비공개 로컬 원장에만 저장.
3. 승인 검사와 위험 분류를 실행 수단(rm/Python/PowerShell) 별 문자열 예외가 아니라 *동일 행위·대상 범위* 기준으로 묶되, **실제 실행 코드/명령 해시도 바뀐 경우 추가 검증**하도록 하라. 서로 다른 명령에 이전 승인을 무단 전용하지 않는다.
4. 정책/검증 레지스트리는 고정된 경로 목록이 아니라 유형별 플러그인처럼 로딩하되, 기본 deny 경계와 정책 서명/접근 권한을 유지. 사용자 본인의 정상 명시 지시와 법적/OS 필수 승인을 구분한다.
5. 실행 결과가 실패/부분 성공이면 사후조건·실제 파일/remote/작업 상태를 다시 읽고, 동일 스코프 내 안전 재시도 또는 blocked로 전이. 승인 재입력을 우선 해결책으로 내세우지 않는다.
6. 기존 `pending`/SessionStart/Stop 흐름에 이번 작업의 미완료를 연결해 다음 세션에 동적으로 이어지게 한다. **새 세션 자동 재개를 실제 운영에서 실측**하고 모델이 수동 지시 없이 수행 가능한 범위를 정직하게 밝힌다.
7. 우선순위는 최신 사용자 목표 P0 > 기존 진행 P1/P2. 고비용 회귀 게이트는 중복 실행하지 않고 표적 시험 우선.

## 4. 테스트 — 특정 사례 이외의 미지 입력을 통과시켜라
다음은 '기존 입력 그대로만 PASS'를 막기 위한 필수 평가. 테스트 데이터는 격리 임시 폴더·가상 승인 DB 사용.
A. 임의로 생성된 서로 다른 두/세 복사본 경로와 이름 → 공통 삭제 워크플로우 재사용; 승인 범위 밖 1개는 보존.
B. 같은 operation에 대해 rm→Python→PowerShell 입력 방식이 달라도 위험 행위 감지는 유지, 승인된 고정 실행 계약만 실행. 새 승인 ID 남발/승인 우회 모두 불합격.
C. 여러 GitHub 저장소/임의 브랜치/미추적·ignored·미Push 파일 → 소스 같다는 주장만으로 삭제 금지.
D. 임의 이름의 안전한 자기 소유 임시 파일 → 종료 시 자동 정리, 다른 세션/사용자/링크 대상 보존.
E. MCP 서버 목록이 바뀌어도 발견/상태/재시도 로직이 코드 수정 없이 동작; 고장난 서버 한 개가 전체 실행을 정지시키지 않음.
F. 임의 요청 ID의 새 review가 changes_requested일 때 자동 큐 생성, 기존 완료 항목 중복 수행 0.
G. 작업 도중 중단/타임아웃/새 세션/워커 0 → 미완료 목표 이어받기, 증거 없는 PASS 거부.
H. 설치 false·실제 경로 존재·게이트 RUNNING·SHA 없음 → 허위 완료 차단. 임의 40자리 가짜 SHA도 검증.
I. 범위/정책/프로그램 해시 변경 및 변조 시 fail closed; 승인 없는 SYSTEM 임의 명령 절대 실행 불가.
J. 사용자 직접 질문이 들어오면 불필요한 회귀 게이트/서브에이전트 종료를 기다리지 않고 짧게 답한다.

각 시험에서 반드시 **수정 전 실패/제약 → 수정 후 결과**, 새로 생성한 미지 경로/새 요청 ID를 사용해 하드코딩 의존이 없음을 확인한다. 전체 회귀는 변경 영향 기반으로 최소 실행.

## 5. 납품과 엄격한 완료 판정
- 먼저 코드 진단 결과: `기존 하드코딩 위치 | 왜 문제인지 | 유지할 보안 상수 | 동적 전환 방식 | 실제 수정 SHA | 검증`.
- 최소 하나의 실제 수직 슬라이스를 **사용자 목표에 대해 운영에서 실행·사후조건 검증**하고 보고. 설계 문서만 작성하면 FAIL.
- 실제 수정 코드와 테스트를 GitHub main에 push, 원격 SHA 확인 후 `.ai-collab/reports/R375.md` 제출. R374 승인·삭제 진실성은 별도 정확한 상태 유지.
- 과도한 아키텍처 재작성 금지. 1인 개발자 시스템에 맞게 기존 코드의 중복과 사용자 수동 부담을 줄이는 방향.
- 보안 우회·사용자 파일 오삭제·승인 DB 위조·무단 범위 확대·'모든 파일 자동 삭제'는 실패.
- 증거가 없는 UNKNOWN을 DONE이라고 바꾸지 않고 다음 실행 가능한 탐색/수정으로 연결.
- ChatGPT 독립 재검토 전 자체 100점·전면 완료 주장 금지.

**핵심: 사용자가 매번 새 예외·경로·승인 번호를 알려 주는 시스템이 아니라, 한 번 지시한 목표와 승인 범위 안에서 시스템이 동적으로 판단하고 끝까지 검증·재개하는 오케스트레이션으로 바꿔라.**
