# R368 — System32 오염 원인 추적, 실제 문제 해결, 재발 방지

## 최우선 사용자 요구
사용자는 왜 불필요하게 Windows System32에 확장자 없는 `powershell` 파일이 만들어졌는지, 누가/어떤 코드가 만들었는지, 왜 삭제하지 못하는지, 앞으로 재발하지 않게 할 방법을 **실제로 구현**하라고 지시했다. Claude CLI는 현재 진행 중인 작업을 고려해 즉시 진행한다. 시뮬레이션·문서·전수조사로 실제 해결을 불필요하게 지연하지 않는다.

## 현재 증거 (과거 성공 주장으로 덮어쓰지 말 것)
- 사용자 제공 최신 Claude CLI 로그: `C:\Windows\System32\powershell`는 `Test-Path=True`로 **미삭제**. 관리자 권한 및 정식 승인 대기. 기존 `appr-713617e80d83` 언급.
- `elevated-task.ps1`·`elevated-runner.ps1` 구현·격리 시험 11개 PASS로 보고했지만 실행 상태 `installed:false`: **실제 설치·운영 확인 안 됨**.
- `test_next_actions_persistence.py` **11 passed**는 해당 모듈 시험 결과일 뿐 전체 회귀/파일 삭제 성공이 아니다. 회귀 게이트는 로그 시점 진행 중, commit/push/전파 완료 미확인.
- 기존 문서 `docs/FINAL_AUDIT_PLAN_2026-11-03.md`는 문제 파일의 생성일을 2026-04-08로 기록하고, 과거 출력 리다이렉션 잔재라는 설명은 **추정**이라고 명시한다. 절대로 범인·원인을 확정된 사실로 보고하지 마라.

## P0 A. 실제 장애를 가장 짧은 경로로 해소
1. 삭제 대상 `C:\Windows\System32\powershell`이 확장자 없는 0바이트 **일반 파일**, 링크·디렉터리·정상 Windows 파일이 아닌지를 실행 직전에 최소 확인한다. `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`는 절대 손대지 않는다.
2. 기존 유효한 승인 요청은 범위/스크립트 해시를 확인하여 재사용하되 Windows UAC와 내부 승인을 구분한다. 해당 승인이 실제로 미완료라면 사용자에게 **단 한 번 검증된 정식 승인 UI/입력**을 제공한다. Windows 승격·UAC는 사용자가 직접 확인한다. OS 승인 우회·승인 DB 변조·훅 무력화 금지.
3. 승인 후 조건부 실제 제거. `Test-Path=False`, 정상 PowerShell 실행, 원래 '앱 선택' 재현 여부를 실측 확인한다. 실행이 막힌 상태에서는 절대로 DONE으로 표기하지 마라.
4. 관리자 실행 계층은 실제 설치 상태와 권한을 확인한다. 미설치라면 '구현 완료'로 보고하지 말고 정식 설치 절차를 실제 실행 가능한 형태로 제공하고 승인 후 적용한다.

## P0 B. 불필요한 System32 파일이 생성된 실제 원인 조사
1. 현행 kit 및 실제 활성 환경의 PowerShell·Bash·Python·Hook·Agent·예약 작업 명령 중 `powershell`/System32에 **확장자 없는 파일을 생성하는** 리다이렉션, 상대경로, 잘못된 작업 디렉터리, 출력 파일 생성, 셸 경로 해석을 우선 좁혀 조사한다.
2. 알려진 생성일(2026-04-08)·수정시각·파일 소유자·ACL·가능한 감사/셸 실행 이력과 당시 코드/커밋을 상호 대조하라. 로그가 없으면 생성 주체를 **UNKNOWN**으로 표시하고 추정하지 않는다.
3. 고장 재현은 **격리 임시 디렉터리만** 사용한다. System32에 새 테스트 파일을 쓰지 말고 기존 시스템 상태를 악화시키지 마라.
4. 직접 원인이 되는 코드가 발견되면 실제 정본을 최소 수정한다. `powershell.exe`의 검증된 실행 경로 사용, 모든 출력 경로 절대화·검증, 관리 디렉터리 오염 방지, 명령 실행 전 작업 디렉터리 검증, 해당 작업에 맞는 출력 리다이렉션 수정을 적용한다.
5. 원인 미확정 시에도 System32에 예기치 않은 파일을 쓰려는 잘못된 경로를 탐지하고 실패시키는 최소 사전 검증 및 재현 테스트를 마련하라. Windows 전체 쓰기 작업을 무분별하게 차단하지 마라.

## P1 C. 실패 중인 작업과 개발 부담 관리
- 현재 진행 중인 회귀 게이트는 실제 PID/종료 상태부터 확인한다. 같은 대규모 게이트 재시작이나 병렬 고부하 테스트 금지.
- `ai-collab-report.py` 백오프 변경, `auto-save-next-actions.py` 개행 수정 등 사용자가 제공한 진행 작업을 보존하고 해당 워커가 수정 중인 파일에 중복 패치하지 마라.
- 이미 실행한 표적 테스트 결과를 재사용하되 코드가 바뀌면 영향 범위만 재시험한다.
- R367과 연동해 **구현됨/테스트됨/실제 설치됨/실행됨/사용자 장애 해결됨/Push됨**을 각각 나눠 보고한다.

## P1 D. 재발 방지 수용 기준
1. 실제 System32 파일의 존재 여부와 정식 삭제 시도 결과를 명확히 기록.
2. 생성 원인에 대해서는 확정 코드 위치·명령·실행 근거 또는 UNKNOWN을 기록. 근거 없는 '리다이렉트 실수' 확정 금지.
3. 원인 관련 격리 시험: 상대경로, `powershell` 명령 shadowing, System32 오출력, 정상 `powershell.exe` 호출, 권한 부족, 거부된 승인, 승인 후 실제 처리 상태 등 필요한 범위.
4. 실제 버그 수정 전 FAIL/후 PASS 및 수정 파일/커밋 SHA. 적용하지 못한 작업은 PARTIAL/BLOCKED를 유지.
5. 현재 GitHub `main`과 활성 Claude CLI 코드 간 변경 일치, commit/push/전파 여부 확인.
6. 사용자에게 **첫 문장에 '삭제됐는가? 예/아니오'**, 이어서 '재발 원인이 확인됐는가? 예/아니오/미확인'을 명료하게 답하라.

## 납품

- 사용자에게 완료된 부분과 권한 승인 대기 부분을 분리해 보고한다.
- 100점은 실제 문제 해결·원인 수정·검증 근거로만 판단한다. 문서 작성/테스트 PASS/설치 스크립트 존재만으로 사용자 목표 달성 완료를 주장하지 않는다.

**이 요청을 현재 Windows에서 실행 중인 Claude CLI가 읽고 실제 해결하라.**


## P0 긴급 추가 — 사용자 질문 즉답 최우선, 작업 진행과 응답 분리 (2026-11-23)
사용자 직접 불만: "삭제 되었냐고", "왜 내가 질문하면 빨리 대답해". 이것은 단순 문장 톤 문제가 아니라 **실행 중 백그라운드 작업 때문에 현재 질문에 답하지 않는 동작 결함**이다.

1. UserPromptSubmit/사용자 입력을 수신하면 **현재 질문에 답할 수 있는 기존 실측 상태**를 우선 판별하라. 긴 조사, 다른 Agent 결과 대기, 회귀 게이트, 신규 스크립트 작성보다 **사용자 질문에 먼저 답한다.** 응답을 위해 불필요한 새로운 도구 실행·전수조사·긴 분석을 시작하지 마라.
2. "삭제됐냐?"의 첫 문장은 측정된 최신 상태를 사용해 **"아니요. 마지막 확인에서 `Test-Path=True`여서 아직 삭제되지 않았습니다. 관리자 승인 대기입니다."**처럼 즉답하라. 이후 상태가 바뀌면 그 최신 관측 시점과 함께 "네, 삭제 확인됨(`Test-Path=False`)"이라고 답하라. 실측이 없으면 "현재 삭제 여부는 미확인"으로 답하라.
3. **예/아니오/미확인 → 단 한 줄 근거 → 필요한 다음 동작 한 가지**의 1~3문장 기본 형식. 상태표·테스트 내역·Agent 요약·다른 결함 보고를 앞세우지 마라. 사용자가 자세히 요청할 때만 상세 보고하라.
4. 답을 먼저 전달한 뒤, 진행 중인 회귀 게이트/수정·테스트·Push는 중단 없이 독립적으로 이어서 수행하라. 사용자 질문과 실행 작업이 충돌하면 안전하게 진행 상황을 보존하되 **답을 테스트가 끝날 때까지 보류하지 마라.**
5. 실패/미완료를 감추려는 완곡어법과 "구현됐습니다" 같은 다른 단계로 질문을 돌리는 답변은 금지한다. 최초 결과로 사용자에게 바로 명확하게 설명하라.
6. 사용자 질문을 작업 지시 또는 추론 긴급 모드로 오인하여 새 승인 ID·대규모 테스트·R 요청을 만들지 마라. 내용이 동일하면 기존 사실 상태를 즉시 전달하라.
7. 기존 Hook·Supervisor·상태 알림·prompt-dispatch가 긴 작업 중 최신 질문을 지연시키는 실제 경로를 확인하고, **읽기 전용 상태 스냅샷 기반 즉답 → 비동기/후속 작업** 흐름으로 최소 개선하라. 무제한 병렬 세션, 새 상주 프로세스는 만들지 마라.
8. 수용 테스트는 (a) 회귀 게이트 실행 중 '삭제됐냐' (b) 백그라운드 Agent 실행 중 동일 질문 (c) 삭제 미확인 (d) 파일 미삭제 (e) 실제 삭제 확인 (f) Hook 반복 알림의 여섯 케이스. 답변 지연은 같은 조건에서 전후 실측하고, 개선 근거 없으면 PASS 금지.

**지금 사용자가 묻는다면 최신 실측상 답은 '아니요, 아직 삭제되지 않았습니다'이다.** 이후 실제 실측으로 업데이트할 것. 지시를 수신한 Claude CLI는 작업을 이어가기 전에 사용자의 질문에 이 사실부터 답하라.
