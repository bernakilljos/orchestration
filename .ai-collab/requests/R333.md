# R333 — 실제 개발 속도 병목 분석 + ack 오확정 방지 (통합 작업)

## 배경
사용자의 최우선 문제는 Claude CLI 개발 속도와 VS Code 체감 버벅거림이다. 사용자가 지시하지 않은 기능 추가로 시간을 소비하지 말고, R332 이후 남은 ack 처리 확정 허점과 성능 진단을 한 번의 작업으로 진행한다. 이 파일은 GitHub에 게시된 외부 개선 제안으로, 자체적으로 추가 결제나 권한 우회 승인을 의미하지 않는다.

## P0. 실제 개발 소요 시간 분석 — 가장 먼저
최근 실개발 작업 10~20건(가능한 표본)의 로그·원장·세션 자료를 **읽기 전용**으로 조사한다. 각 요청별 전체 경과 시간을 가능한 범위에서 아래 단계로 분해한다.
- 메인 Claude 모델 응답 대기, 실제 토큰 생성/출력 시간
- 서브에이전트·멀티에이전트 시작, 실행, 대기, 결과 취합과 중복 탐색
- Hook/StatusLine, Supervisor, 검증·테스트, Git·push·전파에 쓴 시간
- CPU/RAM/디스크 경합, VS Code 터미널 렌더링·입력 지연
- 유료/무료 모델별 호출 횟수와 입출력 토큰(확인 가능한 것만)
- 직접 처리 vs 위임 vs 병렬 처리의 품질(재작업/실패/요구사항 충족)과 시간

병렬 태스크의 소요 시간을 단순 합산해 실제 경과 시간으로 오해하지 말 것. 유효한 로그가 없으면 미측정으로 표시하고 숫자를 만들지 말 것. 토큰 비용과 로컬 CPU 부하를 구분할 것.

이전 측정치인 모델 대기 중앙 4.0초(p90 9.9초), 로컬 Hook 중앙 68ms, 여유 RAM 5.6GB+는 **당시 표본**일 뿐 원인 확정이나 현재 수치가 아니다.

## P1. 서브에이전트 위임 정책의 성능 검증 및 최소화
실제 실행 경로와 규칙(subagent-delegation, execution-contract, dispatcher, Supervisor)의 조건을 조사하라.
- 파일 5개/구현 500줄 등의 고정 위임 기준이 과도한 호출을 유발하는지 확인
- 동일 코드 중복 읽기, 중첩 Agent, 같은 파일의 동시 작업, 독립 검증 중복 탐지
- 불필요한 병렬화가 더 느린 실제 사례 확보
- 가능한 저위험 정책 개선: 기본 직접 실행, 독립성이 입증될 때만 최대 2개 수준으로 위임, 성능·품질 증거가 있을 때만 확대
- 숫자 제한을 무조건 강제하거나 기존 기능을 제거하지 말고 현재 작업별 비용과 품질을 기준으로 적응형 선택
- 추가 유료 모델 호출 없이 기존 로그/격리 로컬 테스트로 검증. 유료 호출이 필요한 비교는 수행하지 않고 승인 필요로 남김.
- 16GB PC를 위한 프로세스/메모리 경합 진단; VS Code 설정이나 시스템 설정은 승인 없이 변경하지 않음.

## P2. R332 ack의 검증 없는 확정 문제 보완
현재 `.claude/scripts/ai-collab-report.py`의 `cmd_ack(target)`는 대상 경로/ID의 inflight 또는 remote blob을 받아 seen으로 확정한다. 요청이 실제로 검증·처리됐다는 증거 확인이 없어 미처리 지시/리뷰가 재전달되지 않을 위험이 있다.
- ack 대상은 협업 폴더 내 유효한 requests/reviews 경로만 허용.
- 미수신 파일을 바로 ack하거나 blob 버전이 바뀐 상태에서 이전 처리를 새 버전의 완료로 확정하는 것 금지.
- 요청의 처리 완료 증거(연결된 작업 커밋·검증 결과 등)와 리뷰의 명시적 검토 판정을 구분하여 확인하고, 불충분하면 확정하지 않음.
- 잘못된 ack, 변경된 blob, 임의 경로, 미완료·승인 대기, 재시도, 정상 처리의 수정 전 실패·후 통과 테스트 작성.
- 기존 report/handled/seen/inflight 호환, 중복 재실행 방지와 운영 원장 무결성 유지.

## P3. 완료 보고 및 파일 정리
- 테스트 숫자만이 아닌 실측 작업 완료 시간의 병목 상위 5개, 지연 기여도, 개선 전후 숫자 및 미측정 사항을 명확히 제시.
- 증거가 없는 개선율이나 완료 주장을 PASS로 적지 말 것.
- 기존 Hook/Agent/상주 서비스 추가 금지. StatusLine 화면 불변, 과잉 전체 테스트 반복 금지(관련 테스트 후 최종 전체 회귀).
- 검증된 소규모 변경만 commit/push. 사용자 직접 명시한 정상 commit/push가 커스텀 Hook 오탐으로 차단되지 않는지도 확인.
- 요청 1건에 보고서 1개만 갱신. 기존 완료 보고서·임시 산출물은 안전한 승인·커밋 증거 검증 뒤 prune하며 운영 DB/원장·보호 데이터와 진행 중 작업은 보존.
- IFRS·ICMAI 전파는 기존 보호·충돌 검증 정책에 따라 처리하고 결과 보고.

## 완료 기준
1. 개발 속도 원인에 대한 로그 근거와 시간 분해(기존 기록이 부족하면 미측정 표기)
2. 과도한 에이전트 호출의 실제 사례 및 필요한 경우 정책 개선
3. ack 실패/성공 양방향 테스트 및 실제 코드 수정
4. 회귀 테스트 결과와 변경 전후 성능 수치
5. 작업 완료 보고서 게시 및 push, 이후 5분 확인 흐름 정상 복구

최우선: 지시문을 늘리고 작은 기능을 계속 추가하는 것보다 **사용자의 실제 개발 작업 완료 속도와 정확도**를 개선하라.
