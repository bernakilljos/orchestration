# R344 — 전 영역 불변 원칙: 속도·성능·품질 동시 최적화, 사례별 하드코딩 절대 금지, 기존 DB 검증 학습 재사용

## 사용자의 최우선 불변 조건
1. **속도·성능·품질**은 개발/테스트/Hook/Agent/디자인/PPT/문서/자동화/상태줄 전 영역의 필수 평가 축. 하나를 높이려고 다른 축을 무단으로 훼손하지 말 것.
2. **사용자 입력 사례에 특화된 하드코딩 절대 금지**. 특정 PPT 이름·포트·페이지 수·모델명·고정 Agent 수·고정 테스트 전수 실행 등 상황 의존적인 데이터를 규칙에 박아 넣지 말 것. 설정/입력/메타데이터/실제 측정으로 동적으로 결정하라.
3. 이것은 정상적으로 필요한 보안 불변식·프로토콜 표준 상수·스키마 식별자·검증된 고정값까지 무조건 없애라는 뜻은 아니다. 합법적인 상수와 위험한 사례별 하드코딩을 명확히 구분하되 사용자 원칙을 우회하는 명목으로 남발하지 말 것.
4. 사용자 명시 지시가 최우선인 1인용 시스템. 사용자 허가 없이 안전·보안·원장·검증의 필수 보호 제거 금지.
5. 이 요청을 받았다고 선행 R338~R343을 중단/재시작하지 말 것. **지금부터 모든 변경에서 이 품질 기준을 즉시 적용**하고, 별도의 R344 통합 검증·개선은 기존 진행 작업 완료 후에 수행하라.

## 실제 코드 근거와 DB 명칭 확인
GitHub 현재 코드에 확인된 영속 DB 경로는 `.claude/state/orca.db`다.
- `.claude/scripts/save_solution.py`: 문제·해결·파일·명령을 `orca.db.problem_solutions`에 저장
- `.claude/scripts/promote-solutions.py`: 조회 빈도 등 재사용 점수 업데이트, **조회 hit는 검증과 다르므로 verified 임의 변경 금지**
- `.claude/scripts/recall-memory.py`: `orca.db` decisions 등 세션 메모리 조회
- `.claude/rules/solution-reuse.md`: verified=0 자동 적용 금지, reusable_score 기준 및 중복 예방
사용자는 `ordb.db`라고 표현했다. **Git 추적 파일 검색에서 그 파일을 확인하지 못했다**. 실제 운영 로컬/환경에 ordb.db가 별도로 존재하는지 정본·경로·스키마를 우선 읽기 전용으로 점검. 이름만 보고 DB를 새로 만들거나 ordb.db=orca.db라고 무단 동일시·마이그레이션·덮어쓰기 금지. 없으면 확인된 orca.db만 사용하고 사실대로 보고.

## P0 — 동적 결정의 공통 계약, SoT
1. 하나의 기존 정책 SoT에 '사용자 명시 지시→근거/현재 맥락→위험도/난이도/자원 상황→실측 학습/검증 기록→선택→결과 검증'의 최소 충분 의사결정 원칙 정리. 문서/PPT 생성·테스트 범위·Agent 실행 수·모델·캐시·Hook 경로·성능 설정 등을 **개별 사례가 아닌 원칙·정책·구성 데이터로 일반화**. 기존 Skill/Command/Hook 호출 흐름에 실제 적용.
2. 프로젝트·고객·문서 유형에 대한 특정 이름/숫자/분량의 if/else 추가 금지. 사용자 입력으로 검증된 제품 수치(예: 포트 9077)는 **그 결과물의 데이터**로 보존 가능하지만 범용 엔진의 고정 규칙에는 넣지 말 것.
3. 합법적 상수, 승인된 보안·일관성 정책, 사용자 고정 선호는 별도 설정/계약으로 표현; 동적 탐색에 실패할 때는 명확한 unknown/BLOCKED 또는 안전한 기본값과 이유를 기록, 조용한 추측 fallback 금지.
4. 처리 시간뿐 아니라 결과 품질·오류 재발·모델 토큰·사용자 수동 재지시 횟수까지 end-to-end로 계측. 반복 수치를 꾸며내지 말 것.

## P1 — 기존 DB를 진짜 학습/재사용으로 연결
1. 운영 DB를 **읽기 전용으로 먼저 감사**: 실제 테이블/인덱스/레코드 유효성·검증 비율·검색 적중률·중복·유효 기간·출처/프로젝트 범위·민감 데이터 포함 여부. 운영 DB 사본/격리 테스트 외 destructive 수정 금지.
2. 새로운 영속 시스템이 아니라 기존 `orca.db`의 verified solution, decisions, failure patterns, optimization history 등을 재사용할 수 있는 현재 구조를 확인하고, **입력 작업에 관련성이 높고 검증된 기억만** 필요한 시점에 읽어 적용. 무관한 이력 전체 주입 금지(토큰/속도 손실).
3. DB의 정보는 LLM weight 학습과 다르다. '기록→검색→검증→적용→성과측정→검증된 결과 저장'의 경험 재사용/피드백 구조로 구현. 조회 횟수나 성공 주장만으로 verified 또는 효과성을 자동 승격 금지.
4. **추천과 실행 분리**: 이전에 성공한 해법도 현 코드 버전·환경·보안·테스트 조건에 맞는지 검사한 후 적용. 위험한 명령·설정·DB 작업 자동 재실행 금지.
5. 최적화 실험의 입력조건/후보/결과/실제 벽시계·메모리/토큰·품질 변화 등을 기존 데이터 모델에서 안전하게 표현할 수 있으면 확장, 현재 스키마에 없는 경우 최소한의 비파괴 호환 확장만. 별도 DB나 무의미한 전용 필드 다량 생성 금지.

## P2 — 3축(속도·성능·품질) 개선을 증거로 입증
- **속도**: 요청→최종 검증 완료 시간, 단계별 대기, subprocess/Hook/UI/PPT 렌더 시간, 테스트 선택 및 중복 실행 수.
- **성능**: CPU/RAM/commit/페이지폴트, cache hit와 유효성, 동시 실행 효율, 토큰·모델 호출, 디스크·SQLite 조회 비용, 시스템 안정성.
- **품질**: 요구 n/n 실이행, 오류 재발/결함 주입 탐지, 보안·승인, 근거 충실도·환각 방지, 편집 가능한 PPT 및 실제 슬라이드 가독성.
- 각 변경에서 검증 품질/사용자 지시 준수는 반드시 보존하며, 개선폭과 자원 비용을 **변경 전후 동일 조건**에서 비교. 측정 실패/표본 부족은 미확인이지 PASS가 아니다.
- 작은 문서 수정에는 가벼운 검증, Hook/DB/보안/원장 공통 코드 변경에는 더 강한 회귀 등 R336의 적재적소 검증 정책을 따른다. 무조건 모든 테스트를 매 단계 반복하지 말 것.
- 서브/멀티 Agent와 병렬 스레드/프로세스 선택도 실측 기반 적응형, DB 동시 쓰기·파일 충돌·과부하 보호. 단순 숫자에 따른 강제 병렬화 금지.
- 읽기 1회에 필요한 캐시/인덱스/반복 파싱 최적화를 점검하되 운영 트랜잭션 일관성·옛 캐시 판정 문제 보호.

## P3 — 다양한 사례로 하드코딩/환각 역검증
1. 서로 다른 시스템, 기술문서, PPT, 테스트, 보안/DB/배포, 개발 코드와 사용자 작업 유형을 대상으로 설정·프로젝트 이름·포트·AI 공급자·페이지 수·Agent 수를 바꿔 시험하여 **전혀 다른 예제에도 동일 엔진이 올바르게 동적 판단**하는지 확인.
2. 원본 근거가 없는 숫자/구조/화살표를 생성하면 실패로 처리. PPT 1건의 스타일을 다른 모든 문서에 적용하거나 품질 점수만 올려 PASS하는 행위 금지.
3. 검증된 이전 해법의 관련성 높음/낮음, 오래된 해법, 검증 안 된 해법, 상충 결과, 다른 프로젝트 데이터 유출, 조회 성능 저하 등 역검증.
4. 이전 사용자가 명시한 보고 시점·안전 권한을 Hook이 덮어쓰지 않는 통합 테스트.
