# R348 — 문제 1개 지적 시 동일 원인 전체 계열을 동적 탐색·검증: 요청의 의미 확장과 구조적 재발 방지

## 사용자 핵심 요구
사용자는 Claude CLI/ChatGPT가 하나의 버튼·PPT·Hook·테스트 문제만 지적받으면 그 항목만 손보고 **같은 원인으로 손상됐을 수 있는 유사 요소를 전수조사하지 않는 것**에 반복적인 불만을 표했다. 특히 사용자가 사례를 직접 나열할 때 그 목록을 하드코딩하는 것도 잘못이다. 목표는 **문제의 의도를 추상화 → 공통 원인 가설 → 실제 프로젝트에 존재하는 같은 원인 계열 동적 발견 → 관련 후보를 충분히 확인 → 최소 수정 → 근거 기반 회귀 검증 → 재발 방지**이다.

현재 진행 중인 R338~R347의 안정화/완료를 우선하고, R348은 **그 이후 수행**. 지금 단계에서는 기존 작업을 끊거나 새 대규모 코드개발에 착수하지 않는다. 사용자가 승인한 범위 내에서만 수정한다. **1인 운영 기준. 비밀정보 저장소 파일 권한 강화 논의 및 개선은 이번 범위에서 제외**한다. 기존 보안 보호를 완화하는 의미는 아니다.

## 먼저 확인할 실제 기존 코드 (중복 프레임워크 구축 금지)
- `.claude/scripts/lib/independent_verifier.py`의 `same_pattern_candidates`: 현재 diff에서 제거된 긴 코드 줄과 동일한 텍스트를 `git grep -F`로 탐색한다. 이는 유용하나 이름/구현이 다른 **의미상 동일한 근본 원인**까지 발견하는 기능은 아니다.
- 같은 파일의 `impact_selection`, `affected_tests`, `regression_gate`: 영향 테스트 선정·공통 모듈·계약 변경의 회귀 검사 기능은 이미 존재하므로 재활용. **테스트 영향 선택 ≠ 동일 원인 결함의 전체 발견**을 혼동하지 말 것.
- `.claude/scripts/adaptive-audit.py`, `audit-15-axes.py`, `audit-all.py`, 기존 recurrence-tracker, `orca.db`의 검증된 해결책/재발 내역, R336·R344 정책과 비교. 운영 DB는 읽기 전용 점검, 새 DB/Agent/Hook/상주 서비스 무조건 추가 금지.

## P0 — 동적 영향 발견의 핵심 알고리즘/절차
1. 사용자 요청을 **증상, 대상, 암묵적 품질 기대, 명시된 작업 범위, 제외사항**으로 정리. 요청 문구의 특정 명사 하나를 '수정 범위 전체'로 오인하지 말 것. 단, 암묵적 확장과 사용자의 명시된 범위 제한이 충돌하면 제한을 존중.
2. 먼저 재현하고 여러 가능한 공통 원인 가설(디자인 토큰/컴포넌트 기본형/데이터 바인딩/계약/공용 함수/검증 정책 등)을 제시한 뒤 확인 가능한 증거로 확정. 예시 목록을 도메인 고정 분기/regex만으로 구현하지 않는다.
3. **이용 가능 신호를 적응적으로 결합:** AST/언어 서버 또는 코드 인덱스, import/call/reference graph, UI 컴포넌트 트리 및 디자인 토큰 사용 지점, 라우트·API·스키마·데이터 흐름, 설정/Skill/Command 연결 관계, git history 및 같은 원인 재발, 검증된 `orca.db` solution. 도구가 없으면 단순 검색+수동 비교로 안전하게 폴백, 탐색 미완료는 표시.
4. 탐색 결과에서 **실제 관련 후보군의 모집단을 산출**하고 각 후보의 관련 근거/확인 상태를 기록: confirmed affected / inspected unaffected / uncertain / excluded with reason. 모르는 것을 0건 또는 PASS로 표시 금지. 관련 전체를 조사하되 저장소 전체 스캔·전체 테스트 무조건 실행 X.
5. 수정은 결함이 증명된 최소 공통 지점부터. 별도 독립 구현마다 동일 패치를 복붙하지 말고 가능하면 공통화. 변경 전후 유사 결함 재탐색으로 누락 후보와 부작용 확인.
6. **차단 게이트:** 유사 결함이 있을 만한 고위험 후보를 검사하지 않은 상태/탐색 도구 오류/사용자가 요구한 범위 미완료라면 전체 PASS 선언 금지. 근거 없는 무한 조사·재귀 확장 방지: 한계는 발견 근거/위험/실측으로 정해 미확인을 명시.
7. 사용자 최신의 명시된 보고 시점/보안·승인 권한/1인 환경 계약을 우선. '전수조사'라는 말로 사용자 지시 없는 외부 시스템/민감 업무 자료까지 뒤지지 말 것.

## P1 — 모든 분야에서 실제 일반화, 하드코딩 역검증
동일 알고리즘을 **서로 다른 기술 도메인에 동적으로 적용**하는 격리 실험을 포함:
- UI의 한 버튼 시각 문제 → 동일 원인/토큰을 공유하는 실제 label/select/input/메뉴 등을 발견하되 실제 공유하지 않으면 제외.
- 하나의 Hook 오탐 → 같은 판정 경로를 공유하는 다른 Hook/명령·승인 흐름 발견.
- 한 pytest 병목 → 동일 재기동/캐시/Fixture/대기 원인을 공유하는 테스트 탐색.
- 한 PPT 문구·다이어그램 오류 → 같은 생성 규칙이 영향을 주는 다른 문서 포맷/내용/시각 검사 루트 확인(R342~R347 중복 구현 금지).
- DB·API·배포·AI 공급자 등이 서로 다른 **새로운 미지의 사례**를 투입해도 특정 이름·포트·형식·컴포넌트 개수 목록에만 의존하지 않아야 함.
실험 샘플은 확인된 기술 사실만 입력, 임의 제품 사실·숫자·관계 창작 금지. 관련 없다면 '무관'으로 판단하는 정밀도 검증도 필수.

## P2 — 속도·성능·품질의 3축 검증
- `same_pattern_candidates`가 발견하는 단순 동일 문자열 사례는 유지, **의미상 동일 결함·변수명 변경·다른 파일 구조·간접 호출까지 찾아내는 recall** 측정. 탐색이 과하게 넓어져 무관 후보가 폭증하지 않는 **precision**과 사람 재검토 비용도 비교.
- 각 테스트 fixture에 **관련 대상의 정답 목록/실제 발견 목록/미검사 목록**이 있어야 하고 발견률·오탐·미검증을 숨기지 않는다. 무조건 100%라고 주장하지 말고 통제된 실험에서만 측정.
- 조사 1회 wall time, 모델 토큰/도구 호출/DB 조회·git grep 횟수, 실제 전체 작업 완료 시간, 변경 후 재발률 측정. 소규모 문제엔 저비용 탐색, 불확실·공용/고위험 변경일수록 넓은 심층 조사. 전수조사가 무조건 전체 저장소 완전 탐색·대형 LLM 다중 호출을 뜻하지 않음.
- **독립 검증:** 사용자 요청→원인→후보 모집단→각 후보 검사 증거→수정 diff→테스트→최종 n/n 연결. 검사 누락이나 유사 결함 잔존을 주입한 역검증이 실제 실패를 만들어야 함.
- 명시 허가 없는 고비용 API 호출·민감 자료 업로드·DB 변경/타 프로세스 종료 금지.

1. 먼저 R338~R347 실제 상태(PASS/PARTIAL/미보고) 확인 후, 이미 해결된 기능과 중복되는지 차분 분석.

3. Claude가 소스 변경·검증·기존 보안 준수·전후 성능 근거와 `.ai-collab/reports/R348.md`를 push.
4. ChatGPT는 기존 연결과 **실제 검토 가능한 시점**에 diff/보고서/테스트 근거를 독립 확인하고 빠진 원인 계열이나 근거 없는 PASS가 있으면 구체적으로 재지시. 이미 검증된 내용의 스타일 핑퐁 금지.
5. **종료 조건:** 적어도 다종 도메인 역검증에서 재현 가능한 precision/recall·탐색 비용 개선, 누락 후보 경고, 증거 연계, 현재 사용자 요구 완전성. 품질·속도·성능을 해치면 되돌리고 이유 기록. 미달은 PARTIAL로 표시.

최종 목적은 사용자에게 '버튼 하나 잘못됐다'고 듣고 버튼 하나만 고치는 것이 아니라 **동일 원인이 미치는 실제 영향 계열을 스스로 밝혀 관련 항목 전체를 정확히 검증하는 오케스트레이션**이다.
