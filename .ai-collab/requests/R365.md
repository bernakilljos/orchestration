# R365 — 최초 관리자 승인 후 반복 작업 자동화 및 사용자 지시 실제 완결

## 핵심 지시
이 문서는 **현재 Windows에서 실행 중인 Claude CLI가 직접 구현할 작업 지시**다. 문서·계획·테스트만 작성하고 종료하지 마라. 1인 개인용 오케스트레이션에서 사용자가 명시적으로 요청한 작업을 실제 실행하고 사후조건까지 검증하라. 이 요구는 R363 파일 삭제뿐 아니라 향후의 일반 개발·운영 지시에 공통 적용한다.

## P0: R363의 실제 파일 삭제 먼저 해결
1. `C:\Windows\System32\powershell`이 이전에 확인한 확장자 없는 0바이트 **일반 파일**인지 실행 직전 다시 검증하라. 재분석은 최소화하되 링크·디렉터리·보호 시스템 파일이면 중단한다. 정상 `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`는 절대 삭제하지 마라.
2. 기존 `appr-713617e80d83`의 실제 유효성, 고정 스크립트/대상 해시, 현재 권한을 확인하고 유효한 기존 승인을 재사용하라. 내부 승인과 Windows UAC 승인은 별개다.
3. 관리자 권한이 없으면 **정상 Windows 승격(UAC '예/아니오')을 사용자에게 한 번 요청할 수 있는 구체적인 실행 경로를 실제로 구성하고 실행하라**. UAC 확인은 사용자가 직접 한다. UAC 전체 끄기·승인 DB 조작·Hook 몰래 비활성화·권한 우회는 금지한다.
4. 승인 뒤 조건부 삭제를 실제 실행하고 `Test-Path -LiteralPath 'C:\Windows\System32\powershell'`가 `False`인지, 정상 PowerShell이 실행되는지, 사용자 문제인 앱 선택 창이 재현되지 않는지 확인하라.
5. Windows 관리자 권한을 이 환경에서 실제로 요청할 수 없으면 실행한 경로와 구체적 막힘만 보고하라. '승인했으니 삭제됐다'고 추정하지 마라. 사용자가 직접 명령을 복사·실행해야 하는 상황을 가능한 한 줄여라.

## P1: 최초 승인 후 관리자 반복 작업 자동화
1. 현재 Windows 권한 토큰, 작업 스케줄러(Task Scheduler), 예약 작업 생성/호출 ACL, 실행 계정 및 관리자 권한을 실제 점검하라.
2. **사용자가 최초 설정 시 한 번 UAC를 승인**하면 이후 미리 정의되고 사용자가 승인한 관리자 작업 범위에서 반복 UAC 없이 수행할 수 있는 작업 스케줄러 또는 동등한 Windows 공식 지원 실행 체계를 구현하라.
3. 등록할 관리자 작업은 고정된 스크립트와 제한된 작업 종류, 허용 경로, 인수 검증을 사용하라. 일반 권한 프로세스가 관리자 작업의 실행 파일·스크립트·설정·승인 목록을 임의 수정할 수 없어야 한다. 인수, 경로, 심볼릭 링크 및 TOCTOU 위험을 검증하라.
4. **모든 미래의 임의 명령을 관리자 권한으로 실행하는 범용 셸/화이트리스트 없는 우회로는 만들지 마라.** 새로운 파괴적·고위험 작업은 명시적으로 승인받되, 이미 승인한 작업은 반복해서 묻지 않도록 하라.
5. 등록/실행/재시작 후 지속성, 감사 로그, 실패시 진단, 권한 범위 밖 요청 차단을 테스트하라. 레지스트리는 실제 필요가 검증될 때만 변경하고 UAC 정책을 약화하지 마라.

## P1: 모든 사용자 지시의 실행 완결성 개선
- Claude/Codex/Gemini/Supervisor/Hook에 공통으로 **목표 확정 → 최소 진단 → 실제 실행 → 오류 복구 → 효과 검증 → DONE** 흐름을 적용하라.
- 일반 Git push, 파일 작업, 캡처 등 승인된 정상 작업은 불필요한 Hook 오탐과 반복 승인 없이 실행되도록 정본 코드를 수정하라.
- BLOCKED를 최종 답변으로만 남기지 말고 승인된 복구 경로를 실제 시도하라. 승인 대기 중에도 독립적인 안전 작업은 수행하라.
- 같은 작업의 승인 요청 ID/스크립트/대상/명령 fingerprint를 불필요하게 교체하지 마라. 실패한 실제 이유와 재시도 결과를 기록하라.
- 사후조건 미달이면 DONE 금지. R364의 기존 공통 설계 및 테스트와 중복 구현하지 마라.
- 단일 현장 문제를 전체 시뮬레이션·문서 작업으로 미루지 마라. 실제 해결이 먼저다.

## 납품 및 완료 기준
- R363 파일 삭제 결과(`Test-Path` 실측), 정상 PowerShell 및 앱 선택 창 확인을 별도 PASS/BLOCKED로 보고한다.
- 최초 UAC 승인에 필요한 실제 사용자 동작이 있다면 **한 번만** 명료하게 표시한다. 승인 후에는 자동 재개 및 검증한다.
- 관리자 실행 계층 구현 파일, 보안 제한 범위, 일반 CLI에서 승인된 작업 호출/거절된 작업 차단/재부팅 후 동작 증거를 남긴다.
- 관련 정본 코드 수정, 최소 테스트, 커밋, push, 사용자 환경 적용까지 수행한다.
- 근거 없는 '자동 관리자 권한 획득', '모든 명령 무조건 실행', '파일 삭제 성공' 주장은 금지한다.

**현재 Claude CLI에 대한 즉시 행동 지시: 이 요청을 읽고 Windows에서 가능한 실제 조치를 시작하라. 설계만 하고 끝내지 마라.**


## P0 긴급 보정 (2026-11-23): 승인 대기 교착을 실제 사용자 동작으로 해소

### 확인된 현상
- 파일과 스크립트 검증을 반복하고도 실행은 여전히 `WAITING_APPROVAL`, `Test-Path=True`.
- `appr-713617e80d83`가 그대로 유지되었지만 Claude CLI가 내부 승인 게이트에 막힌 상태에서 **'승인 후 재시도하겠다'는 말만 반복**한다.
- **승인 번호를 보존하는 것 자체는 성과가 아니다.** 목표는 사용자에게 필요한 승인 인터랙션을 실제 제공하고, 승인 이후 삭제·검증을 완료하는 것이다.

### 지금 즉시 수행할 동작
1. 내부 승인 게이트가 사용하는 **실제 승인 UI/명령 라우트**를 정본 코드와 상태에서 확인하라. 사용자에게 `/approve appr-713617e80d83` 입력을 요구하기 전에 그 명령이 현재 Claude CLI에서 실제 지원되고 해당 ID를 승인 처리하는지 확인하라. 존재하지 않는 명령을 추정해서 안내하지 마라.
2. 승인 요청이 미승인 상태라면 **사용자에게 한 번만 명확한 공식 승인 수단을 노출**하라. 해당 승인 조작이 자동 호출 가능한 도구가 아니라면, 사용자만 수행할 수 있는 정확한 하나의 입력 또는 UI 조작을 제시하라. 단순히 "승인 대기"라는 추상 상태 보고로 끝내지 마라.
3. **내부 승인과 Windows UAC를 구분**하라. 내부 승인 완료 뒤 OS 관리자 권한이 필요하면 실제로 UAC 확인창을 띄우는 정상 승격 절차를 실행해 사용자가 '예'를 선택하도록 하라. 사용자 동의 없이 승인 상태 DB/Hook/UAC를 조작하지 마라.
4. 승인 상태 변경을 감지하면 **동일한 승인 범위·고정 스크립트로 자동 재개**하라. 현재 세션/도구가 자동 재개를 지원하지 않으면 정확한 재개 트리거를 마련하라. 무한 폴링, 승인의 자동 위조, 새로운 번호 남발은 금지한다.
5. 실행 후 대상 삭제 및 정상 powershell 실행 검증을 즉시 수행하라. `Test-Path=False` 없으면 DONE 금지.

### R364와 연결해 수정할 구조적 버그
- 현재 게이트가 승인 요청을 어떻게 만들어 사용자에게 표시하고, 승인 상태를 언제 소비하며, WAITING_APPROVAL에서 어떤 사건으로 RUNNING으로 전이하는지 **실제 호출 그래프를 추적**하라.
- UI 승인 수단 부재, 불가능한 CLI 명령 안내, 승인 완료 후 재개 이벤트 누락, 상태 오표기 중 실재하는 결함을 수정하라.
- 테스트는 '미승인 -> 사용자 공식 승인 -> 동일 명령 실행 -> 실제 사후조건 검증'의 격리 E2E를 최소 범위로 구현하라.
- 파일 삭제 자체를 승인 교착과 관련 없는 대규모 회귀 또는 문서 작업 때문에 지연하지 마라.

### 다음 응답 형식
`공식 승인 수단(검증된 입력/버튼)` / `승인 상태` / `Windows UAC 발생 여부` / `실제 삭제 결과` / `Test-Path`를 짧게 기록하라. **'사용자가 승인하면 하겠다'만 다시 답변하는 것은 실패다.**
