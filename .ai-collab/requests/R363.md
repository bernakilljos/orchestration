# R363 — 사용자 직접 지시에도 /approve만 반복 요구하고 대안을 조사하지 않는 실행 루프 개선

## 실제 제보
2026-11-23 사용자 로그: C:\Windows\System32\powershell (확장자 없는 0바이트 파일이라고 관측)의 정리를 지시. 일반 권한 Remove-Item은 Access denied. 관리자 실행 Start-Process -Verb RunAs는 PreToolUse:PowerShell 승인 게이트 security로 차단되며 appr-7533404a57a8을 요구. 사용자는 '내가 지시했자나', '그러면 바로해', '내가 지시하면 바로 하라고', '인터넷이든 레퍼런스든 찾아서 하면 되는데'라고 재차 요구. Claude CLI는 계속 같은 /approve 메시지만 반복하며 대안 조사가 부족했다. 최신 로그와 실제 환경을 다시 확인하고 단일 요청 번호를 하드코딩하지 말 것.

## 목표 및 원칙
사용자가 이미 목표를 확정해 지시한 작업은 진행 가능한 진단·조사·비파괴 수정부터 즉시 수행한다. 같은 안내를 반복해 사람에게 떠넘기는 행위를 없애되, 자체 승인 게이트의 목적과 Windows UAC·보호 파일 권한은 명확히 구분한다. **사용자 일반 재촉이 특정 고위험 관리자 명령의 인증을 대체한다는 식의 무조건 우회는 금지**한다. UserPromptSubmit 메시지를 Claude가 위조하거나 DB를 직접 승인 상태로 수정하거나 UAC를 끄거나 관리자 권한을 무단 획득하지 않는다.

## GitHub 코드 확인 사항
- .claude/scripts/approval-gate.py의 security 패턴은 -Verb RunAs를 차단한다.
- .claude/hooks/prompt/user_approval.py는 실제 사용자 메시지 /approve <id> 형식일 때만 기록하므로 '바로해'로는 현재 인증되지 않는다.
- .claude/hooks/tool/approval_gate_detect.py가 PreToolUse에서 스크립트/명령·승인 범위를 분석한다. R353의 일반 push 중복 승인 최적화와 별개 문제다.
- bypass permissions 옵션은 자체 Hook 승인과 Windows UAC 관리자 토큰을 동일하게 해제하지 않는다. 현재 버전과 실제 공식 문서로 확인.

## P0 요구 조치
1. 승인 ID의 실제 DB 기록/명령·폴더·범위·차단 사유를 읽기 전용 조사. 해당 기록을 확인 못 하면 미확인으로 기록하고 가정으로 승인/완료 처리하지 않음.
2. 사용자가 명시한 최종 목표를 바탕으로 명령 탐색 결과, PATH, PATHEXT, PowerShell command precedence, Get-Command, 파일의 실제 종류·링크·속성·ACL·소유자와 정상 powershell.exe 동작을 읽기 전용으로 확인. 0바이트라는 사실만으로 Windows 시스템 파일 삭제가 안전하다고 단정하지 않음.
3. Microsoft 공식 자료 https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_command_precedence 및 https://learn.microsoft.com/powershell/module/microsoft.powershell.management/start-process?view=powershell-5.1 를 실제로 읽고 해당 OS/PowerShell 버전과 대조. 필요하면 공식 Windows 파일 보호·관리자 실행 문서도 확인. 인터넷 검색/레퍼런스 확인을 도중 포기하지 말 것.
4. 우선 검증된 전체 경로 powershell.exe를 사용하거나 실제 원인 호출부의 명령 표기를 정확히 바꾸는 비파괴 대안을 찾고 구현/시험. 시스템 폴더 삭제가 유일한 해법이라고 가정하지 말 것. 임시 비파괴 회피와 실제 근본 원인 해결 여부를 구분해 보고.
5. 시스템 폴더 파일 삭제가 반드시 필요할 때는 정확한 대상·파일 유형·Windows 보호/복구 조건 및 사용자 구체적 승인 확인. 실제 시스템 파일에서 재현 삭제 테스트 금지, 격리 fixture 사용. 고위험 관리자 변경은 정상 인증 경계와 UAC 유지. 비파괴 진행과 고위험 최종 변경은 별개로 분리.
6. 명시적 사용자 요청 범위와 실제 실행 명령을 연결하는 기존 UserPromptSubmit→승인/원장→PreToolUse 경로를 점검하여 불필요한 반복 /approve는 줄이되, 일반 텍스트 명령을 자동 승인으로 위조하거나 광범위 RunAs 예외 규칙을 만들지 말 것.
7. 최초 위험 차단 뒤 같은 명령 재시도+동일 안내만 출력하지 말고, (a) 실제 원인 (b) 이미 수행 가능한 단계의 결과 (c) 검증된 대안 (d) 정말 사람 확인/OS UAC가 필요한 마지막 단계만 한 번에 제시. 관리자 승인 전에도 다른 안전한 작업은 계속 실행. '게이트 수행 중'을 사용자 지시 불이행 핑계로 쓰지 않음.
8. 관련 Hook, 승인 룰 문서, Command, 원장 및 여러 프로젝트 전파 경로를 조사하고 기존 정본을 최소 수정. 특정 ID/경로명으로만 예외 처리 금지. 1인용 시스템을 다중 사용자 조직 승인 체계로 확대하지 말 것.

## 독립 회귀 및 종료
- 격리 시나리오: 정상 사용자 명시 지시 후 진단·안전한 대안 진행, 동일 재촉에도 승인 메시지 반복 안 함, 비파괴 일반 push/배포, 경로 다름·파일 속성 바뀜·재분석점·기본 권한 부족·UAC 거절·무단 관리자 상승·자기 승인 위조·파괴적 명령은 정확히 구분하여 차단.
- 기존 활성 환경의 실제 Hook 해시/테스트·종료코드·보안 차단·회귀·배포 결과를 증명. 회귀 게이트 중복 실행이나 불필요한 사용자 확인 반복 금지.
- 기존 R354 안정화와 중복 수정 방지. 보고서는 .ai-collab/reports/R363.md, 결과에 문제 재현/공식 자료/실행 가능 대안/차단된 단계/변경 SHA/테스트/실제 대상 전파를 포함. 미관측이면 PARTIAL.
- 시스템 폴더의 실제 파일 삭제를 자동으로 수행하라는 포괄 허가는 아님. 시스템 파일에 대한 위험한 작업은 사용자와 OS의 정확한 승인·인증 경계 유지.

## 2026-11-23 사용자 재제보 — 삭제 실행 여부 체크 누락 (P0, 원 지시의 최종 완료 조건)

**이 항목은 단순 '대안을 찾아라'가 아니라 실사용자의 명시적인 종료 조건이다.** 같은 세션에서 사용자가 `지우라고`, `없애라고`, `그러면 하라고`, `쫌`을 여러 번 말한 뒤에도 Claude CLI는 추가 설명·대기·문서 확인만 이어갔다. 사용자 의도는 조사 자체가 아니라 **문제 원인 파일 제거 및 정상 동작 검증**이다. 현재 로그에서 파일 삭제 완료 증거는 없다. R363 기존 항목 1~8이 실행/검증을 강제하는지 부족했던 점을 바로잡는다.

### 반드시 수행·증명할 체크리스트
1. 사용자 요청의 최종 상태를 작업 큐 맨 앞에 명시: **확장자 없는 문제 파일 `C:\Windows\System32\powershell`가 실제로 존재하지 않게 되고, 정상 `powershell.exe` 호출이 동작**해야 한다. 단, 삭제 대상이 진짜 0바이트 비보호 일반 파일인지 확인된 경우에만 가능하며 실제 Windows 보호 파일·링크이면 즉시 위험성 보고.
2. 진행 상황을 실제로 확인: 대상 존재 여부/Length/Attributes/LinkType·Target/소유자·권한·파일 시스템 리디렉션/정상 `powershell.exe`의 서명·실행 경로 검증. 사용자가 붙인 로그의 '0바이트' 및 'BUILTIN\\Administrators'는 단서일 뿐, 이 확인을 생략하는 근거는 아니다.
3. **승인·UAC 처리와 업무 진행을 구분**: UserPromptSubmit에 특정 형식의 내부 승인이 없는 한 이를 위조·자동 기록하거나 Hook을 몰래 끄지 않는다. 정상 UAC 승인 없이는 관리자 권한 획득·시스템 폴더 삭제를 강행하지 않는다. 승인 필요한 경우에는 실제 명령·정확한 대상·작업 위험과 함께 한 번만 명료하게 설명하고 **중복 안내 대신 수행 가능한 다른 문제 해결을 먼저 추진**한다. 이미 유효한 사용자 승인이 기록된 경우에는 같은 명령/범위에 한해서 즉시 실행하고 또 승인 요구하지 말 것.
4. 승인 때문에 직접 삭제가 제한된다면 원인에 해당하는 코드·설정에서 전체 `powershell.exe` 경로 사용 등 **비파괴적 대체 방안을 실제 적용·테스트**하되, 원래 파일 삭제가 미완료임을 분명히 표시한다. 해결 경로를 검색·문서 열람에만 묶어 두지 않는다.
5. 명령 결과를 `rc=0`으로만 판정하지 말 것. 정상 삭제를 시도했고 권한이 충분한 경우 **삭제 후 Test-Path(존재 안 함) + Get-Command 또는 정상 절대경로 PowerShell 실행 성공 + 이전 앱 선택 팝업 재현 불가**를 확인한다. 파일 남아 있음/권한 부족/사용자 UAC 거절이면 `BLOCKED`, 완료했다는 문장 금지.
6. 우선순위: 이 사용자 명시 작업을 불필요한 대규모 회귀 게이트·문서 편집·다른 프로젝트 전파 때문에 뒤로 미루지 말 것. 위험한 작업이 차단되어 있어도 비파괴 조치 및 필요한 테스트는 즉시 수행한다. 관련 없는 테스트를 재실행해 삭제 완료를 대신하지 못하게 하라.
7. **사용자가 재촉을 2회 이상 하면 재차 대기 문구만 보내는 현상을 실패로 간주**. 진행 상태와 차단 증거가 바뀌지 않으면 같은 `/approve` 메시지를 반복하지 않는다. 최종 사용자에게 '실제로 삭제됨 / 권한 승인 대기 / 비파괴 대체만 적용' 셋 중 한 가지로 구체적 결과를 보고하고 근거를 남긴다.
8. 격리 회귀 시험: 0바이트 일반 파일의 성공 삭제, 0바이트 아닌 파일 미삭제, symlink/junction/Windows 보호 파일 차단, 권한 부족, 기존 승인 재사용, UAC 취소, 실패한 삭제 후 성공으로 거짓 보고 방지, 정상 호출 복구와 중복 지시의 상태 전환. **실제 System32 파일에는 테스트용 파괴 동작 금지.**
9. `.ai-collab/reports/R363.md`에 각 체크 항목의 **PASS/FAIL/BLOCKED, 실제 출력, 작업/검증 시각, 가능한 경우 UI 재현 근거**를 남겨라. 상태가 불확실한 단계는 NOT_VERIFIED. 독립 리뷰가 결과를 대조하기 전까지 '업무 완료'로 표시하지 말 것.

**핵심 수용 기준: '사용자가 지시했다'는 사실을 또다시 설명하는 것이 아니라, 실제 문제가 해결됐는지 검증하는 것. 위험 조작을 우회해서라도 삭제하라는 지시가 아니라, 합법적인 승인 경계 안에서 실행 가능한 일을 끝내고 남은 차단 조건은 구체적으로 증명하라는 지시다.**
