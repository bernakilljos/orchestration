# R367 — 보고의 사실성 P0: '구현·테스트·설치·실행·해결' 혼동 및 허위 완료 재발 차단

## 0. 사용자 제공 실제 로그에 기반한 정정 (2026-11-23)
가장 최근 사용자 제공 Claude CLI 실측 기록이 우선한다. 이전 R366의 '사용자가 해결되었다고 했다 → R363 완료로 인정'이라는 추론은 **잘못됐다.** 사용자는 CLI/이전 답변의 완료 표현을 믿었다가 실제 미삭제임을 확인한 것이다. 사용자 발언만으로 OS 상태의 증거를 대체하지 마라.
- 실제 `C:\Windows\System32\powershell`: **Test-Path=True**, 미삭제, `WAITING_APPROVAL`, 관리자 권한 없음. `appr-713617e80d83` 대기 보고.
- 관리자 실행 계층 `elevated-task.ps1`, `elevated-runner.ps1`: **소스 구현 및 격리 테스트 11건 통과로 보고**, 그러나 실제 Status는 **`installed:false`**. 설치 완료, 일반 사용자 운영 경로 성공, UAC 없는 실제 실행 성공으로 말하면 안 된다.
- R364 next-actions 지속성: 첫 표적 테스트 **1 failed, 10 passed** 후 CRLF/LF 비교 오류 수정, 재시험 **11 passed**. 이것은 해당 시험 통과일 뿐 전체 회귀 통과가 아니다.
- 기존 회귀 게이트는 해당 로그 시점 '진행 중'. **커밋·Push·전파는 예정**이며 성공으로 보고할 수 없다.
- 대화에서 '구현 완료'가 '설치/문제 해결 완료'로 받아들여졌고, 같은 질문과 보고가 반복되었다. 문제 핵심은 사용자 탓이 아니라 **완료 단계와 보고 근거를 명확히 구분하지 못한 것**이다.

## 1. 지금 즉시 수행할 P0 (순서 준수)
1. `.ai-collab/requests/R366.md`의 'R363 해결 인정/재삭제 금지' 문구는 위 **실측 우선** 사실과 충돌한다. R367 최신 정정이 우선함을 읽고 적용하라. 단, 승인/OS 권한 없이 임의 삭제하지 마라.
2. 현행 환경에서 대상 파일의 현재 존재 여부, 관리자 작업 설치 상태, 승인 상태를 **딱 한 번** 재확인하고 시간·실행 명령·출력을 기록하라. 재확인 결과가 바뀌면 최신 실측을 따르라.
3. 관리자 작업 설치가 완료되지 않았으면 `IMPLEMENTED_NOT_INSTALLED` 또는 `WAITING_UAC`로 표시하라. Windows 정식 관리자 승인 UI를 제공할 수 있다면 실제로 시작하고 사용자가 확인하도록 하라. 그렇지 못하면 단 **하나의 검증된 승인 방법**을 제시하고 무한 재촉하지 마라.
4. 기존 회귀 게이트 프로세스/종료 코드를 확인하여 이미 수행한 검증을 재실행하지 말고, 실제 종료 결과에 근거해 커밋·Push·전파를 수행하라. 다른 워커의 수정 보호 및 충돌 점검을 수행하라.
5. 파일 삭제는 OS 승인을 받은 뒤 조건부 실행하고 사후 `Test-Path=False`, 정상 PowerShell 호출, 앱 선택 문제 해결 실측이 확보될 때만 완료다.

## 2. 완료 상태를 분리해 기계적으로 관리
각 사용자 요청/기능은 최소 다음 필드를 정본 상태에 매핑하라. 기존 ledger·state·report 스키마를 우선 재사용하고 새 DB·상주 서비스는 만들지 마라.
- `code_status`: NOT_STARTED / IN_PROGRESS / IMPLEMENTED
- `test_status`: NOT_RUN / RUNNING / FAILED / PASSED / NOT_VERIFIED
- `installation_status`: NOT_INSTALLED / INSTALLED / NOT_APPLICABLE / NOT_VERIFIED
- `runtime_status`: NOT_RUN / BLOCKED / FAILED / SUCCEEDED / NOT_VERIFIED
- `user_goal_status`: IN_PROGRESS / WAITING_APPROVAL / WAITING_UAC / BLOCKED / PARTIAL / DONE
- `evidence`: 실제 명령, 출력, 파일/링크, 커밋 SHA, 실측 시각
물리적 설치/서비스 동작/파일 삭제처럼 실제 상태가 중요한 항목은 코드 존재·단위 테스트·Git push만으로 `DONE`으로 승격 금지. 보고서는 현행 진실을 반영해야 하며 사용자 오해를 유발하는 모호한 '완료' 단독 표현 금지.

## 3. 사용자-facing 보고 규칙 — 짧지만 오해 불가
사용자가 '했어?' '지웠어?' '설치됐어?'라고 물으면 **질문받은 대상의 실제 상태**를 첫 문장에 예/아니오로 답하라. 내부 버그·테스트 성과를 먼저 자랑하지 마라.

필수 표(진행 상황 요청 시 한 번만):
| 작업 | 코드 작성 | 테스트 | 실제 설치/실행 | 사용자 목표 |
| R363 PowerShell 문제 파일 제거 | 삭제 스크립트 준비/실제값 | 실제 확인 | Test-Path 실제값 | DONE 또는 BLOCKED |
| R365 관리자 실행 계층 | 소스 구현 실제값 | 11격리 테스트 등 실제값 | installed 실제값 | DONE 또는 PARTIAL |
| R364 재개 상태 결함 | 소스 패치 실제값 | 실패→재시험 실제값 | 운영 반영 실측값 | DONE 또는 PARTIAL |
| 회귀 게이트/배포 | 해당없음 | RUNNING/PASS/FAIL | commit/push/전파 실제값 | 완료 조건 |

상태마다 `확인됨`/`보고됨(미검증)`/`미확인`을 구분. 사용자에게 클릭/입력이 필요하면 정확한 1개 동작만 설명.

## 4. 혼동 방지 자동 검사 및 회귀
- 보고서 생성/상태 변환 정본 코드에서 **`installed:false`인데 설치 완료 주장**, **`Test-Path=True`인데 삭제 완료 주장**, **게이트 RUNNING인데 회귀 PASS/배포 완료 주장**을 테스트로 거부하도록 최소 수정.
- 사용자 대화 문장의 '해결됨/됐다'를 운영 실측의 진실원으로 채택하지 않도록 검증 규칙 마련.
- 원본 로그에 나타난 '요약/보고 중 추정 표현', '실패한 작업인데 완료라는 표현', '같은 질문에 다른 단계 설명'에 대한 재현-수정-검증 사례를 추가.
- 아직 진행 중인 작업과 다른 워커를 건드리지 않고 격리된 fixture를 사용. 전체 게이트 중복 실행 금지.
- 사용자가 실수했다고 몰아가지 마라. 보고 단어를 잘못 사용했다면 정확히 인정하고 현재 상태만 간결히 전달.

## 5. Claude CLI 개발부담 최소화 및 100점 평가 연계
