# R351 — 저장소 전역 뒤늦은 누락·반복 검증·중복 실행에 대한 종합감사와 일괄 개선

## 사용자 요구
하나의 문제를 고치려다 다른 누락을 뒤늦게 발견해 커밋/검증을 5~6번 반복하는 구조를 저장소 전체에서 동적으로 찾아 해결하라. 예시 항목을 하드코딩하지 말고 공통 원인과 호출/의존 관계를 찾아 동일 계열 모두 조사. 한 번에 해결 가능한 관련 항목을 묶어 작업하고 반복 핑퐁/중복 요청은 피할 것.
1인 사용자 개인용. 비밀정보 저장소 파일 권한 강화는 이번 범위에서 제외하되 기존 보안·승인 보호는 유지. 속도·성능·품질 동시 개선, 불필요한 Agent/Hook/서비스 추가 금지. 현재 R350 포함 선행 작업의 안정화 이전에는 읽기 전용 진단만, 실제 수정은 선행 안정화 후.

## GitHub 코드 감사에서 확인된 사실과 위험 후보 (현재 코드 다시 확인 후 중복 수정 금지)
F1. .claude/hooks/pre-commit-full-check.sh 와 pre-commit-infra-check.sh 는 인프라 변경 시 동반 문서 요구조건이 다름: 전자는 guide.txt를 요구하고 CLAUDE.md stats 갱신/marketplace/settings/BUILD/회귀 지문까지 검사, 후자는 guide.txt 또는 CLAUDE.md 또는 setup/BUILD.md 한 파일 이상이면 통과. 실제 둘 다 호출되는지는 tool-dispatch/settings/Native hook 호출 추적 없이는 미확인. 판정 기준 불일치와 중복 실행을 검증할 것.
F2. pre-commit-full-check.sh 의 검사 경로 안에서 auto-update-stats.sh 를 호출하고, auto-update-stats.sh 는 CLAUDE.md를 실제 수정하는 sed 경로가 존재. 최종 commit guard의 읽기 전용 원칙과 충돌하는지 격리 재현하고, 필요한 쓰기는 사전 준비 단계로 이동 검토. 실제 갱신 발생 여부는 환경/날짜에 의존하므로 무조건 발생했다고 주장 금지.
F3. sync-plugins.py는 plugins에서 .claude 쪽으로 shutil.copy2하는 경로가 존재하고 drift 경고 표시 조건이 check 또는 verbose일 때. source-of-truth/반대쪽 미반영 수정이 sync로 덮일 수 있는지 격리 복사본에서 테스트. --prune은 orphan unlink 경로이므로 운영에서 실험하지 말 것.
F4. independent_verifier.py 의 code_fingerprint 와 pre-commit-full-check.sh 내 staged tree/code_tree 재사용 판정 비교. 두 구현의 확장자/경계가 동일한지, JSON plugin 변경·문서-only·Git index race·배경 worker 수정·검사 후 변경을 구분하여 stale 재실행과 위험한 오래된 PASS 재사용을 동시에 방지.
F5. integrated-audit.py 여러 검사축에 golden-test.py 반복 호출 경로가 존재. 실제 실행 호출 회수와 소요 시간 조사; audit-all/adaptive-audit/weekly-audit/pytest/smoke-test/Stop/post-impl/CI에서 동일 불변 입력의 중복 시험·상태 변화를 찾아 안전한 공통 증거 재사용. 결과 캐시 유효성을 입력/환경/테스트 버전으로 검증하고 실패나 중단을 PASS로 재사용하지 말 것.
F6. plugin.json↔marketplace.json, Hook↔settings, commands/skills↔배포 사본, setup↔BUILD, source↔generated output, request↔ledger↔report, CI↔로컬 검사 등에서 동일한 late-discovery/write-after-verify/중복 의무/실패 은폐/과도한 반복을 찾아라. grep으로 발견되는 except/exit 0/|| true는 문맥 확인 후 정상적인 예외와 실제 실패 은폐를 구분. R346에서 수정한 CI를 다시 만드는 일 금지.
F7. 사용자 승인한 git push/캡처/완료보고 지시를 불필요한 Hook·Stop·범위 락이 차단하는지, 같은 요청을 poll/worker/retry가 중복 재진입하는지, 환경별 Windows CRLF·Git Bash·Python 버전 때문에 false stale이 발생하는지 조사.

## 강제 조사 방법
1. GitHub 추적 파일 약 6,780개(그중 docs/ 약 5,072개) 기준 전체 구성 지도를 만들되 docs 산출물을 매번 전량 열어보는 낭비 금지. 소스·설정·Hook·worker·검증·DB·문서 생성·plugin inventory에 대해 파일수, 실제 호출 및 데이터흐름, 제외범위와 근거를 기록. 이는 ChatGPT가 확인한 tree 크기이며 수행 시에는 최신 tree를 다시 확인할 것.
2. 요청→계획→변경→파생 파일→동기화→stage→회귀→commit→push→report→재검토 상태 그래프, Hook/검사/worker 자식 호출 그래프, 동일 규칙의 중복 구현 그래프를 기존 코드와 메타데이터에서 동적으로 추출. 특정 파일명/포맷/포트만 나열하는 if-chain이 전수조사의 전부가 되어서는 안 됨.
3. 동일 원인 계열마다 후보 모집단 N, 점검 N, 발견된 실제 문제 N, 정상/미검증/제외 사유를 증명. 정적 소스 결함과 실제 실행 재현 결함을 구분하고 단지 위험 가능성을 완료 실패로 단정 금지.
4. 고위험부터 격리 fixture로 재현한 뒤 공통 원인 지점에 최소 수정. 안전한 사전 preflight로 필요한 동반 변경을 한번에 준비; 최종 commit/validation gate는 가능한 읽기 전용이며 현재 지문과 검증 증거만 확인. 실제 소스 변경 뒤 필수 시험은 재실행하도록 안전 유지.
5. 시나리오: manifest/marketplace 누락과 정상, guide/stats 갱신, settings 신규 hook, source/destination drift, --prune dry fixture, 문서-only, 시험 후 stage 변경, 2 worker의 동시 수정, 중복 Golden Test, 회귀 실패, 승인 필요한 명령, 외부 연결 장애, CRLF. 이는 샘플이며 실제 새 위험 원인을 발견하면 동적으로 확장.
6. 변경 전후 commit 시도 수·Hook 차단 횟수·중복 시험 호출 수·wall time·CPU/RAM·토큰·오탐/누락·실제 검사 탐지력을 같은 환경에서 측정. 무작정 전체 테스트·새 감시 프로세스·sleep 추가·보호 우회 금지. 정상 오류가 실제로 차단되는 역검증 필수.
7. 공식 자료를 실제 읽어 현재 환경과 대조: Git hooks https://git-scm.com/docs/githooks ; Git index https://git-scm.com/docs/git-update-index ; pytest cache https://docs.pytest.org/en/stable/how-to/cache.html ; Python subprocess https://docs.python.org/3/library/subprocess.html ; Claude Code hooks https://code.claude.com/docs/en/hooks . 불필요한 외부 검색은 피하고 내부 자료·기밀 외부 전송 금지.
