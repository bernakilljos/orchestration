# R339 — 회귀 게이트 420초/메모리 대기 300초의 다음 구조적 최적화 (품질 보존)

## 사용자 의도·진행 순서
R334에서 pytest 구간 571.7초→417.1·426.6초로 줄인 것은 성과이지만 최적화 한계라고 가정하지 않는다. **기존 검사 강도·오류 탐지력은 보존하면서 실제 벽시계 시간을 추가로 단축할 방법을 끝까지 조사**한다.
- R335 사용자 지시 준수, R336 적재적소 검증, R337 적응형 에이전트, R338 5영역 개선→마지막 자동화의 기존 우선순위와 충돌하지 않게 **선행 작업을 먼저 마무리하고** 이 후속 작업을 수행. R336에서 이미 해결한 범위별 검증 선택을 중복 구현하지 않는다.
- 개인 1인용 시스템이다. 신규 상주 서비스/Hook/Agent, 다중 사용자용 인프라·무의미한 설정·문서 누적 금지.

## R334에서 확인한 정확한 근거
- 전체 회귀 pytest 767개, 개선 후 417.1·426.6초 (2회), 변경 전 깨끗한 표본 571.7초 1회.
- 상위 25개 테스트 합 145.8초, 느린 후보 `test_regression_gate_pass_regression_preexisting_and_dirty` 약 11.4초, `test_lifecycle_protects_active_and_retained` 약 8.1초.
- 별도 **게이트 벽시계 747초 중 300초는 `_wait_memory_for_heavy` 메모리 대기**. commit 메모리 약 86.7% 상태에서 75% 이하를 기다리다 상한 도달 후 진행했다고 보고. 이 대기는 실제 pytest 실행 구간과 구분해 측정해야 한다.
- R334의 공유 캐시/소스 신선도 보호(옛 pyc로 가짜 PASS 차단)는 유지해야 한다.

## P0 — 테스트 실행 외의 메모리 대기 300초 분석
1. `_wait_memory_for_heavy`의 호출 지점·사용 메트릭(시스템 available, commit %, 프로세스 작업집합, 실제 여유 메모리)·기다림 트리거와 한계 조건을 재현하라. '86.7%라 무조건 위험' 같은 근거 없는 추측 금지.
2. Windows 메모리(commit charge/limit와 물리 RAM)를 혼동하지 말고, 실제 안전 여유/페이지 폴트/스왑 징후·동시 프로세스 부담을 근거로 판단. 보호용 메모리 게이트를 무조건 제거하거나 대기 시간을 임의로 0으로 바꾸지 말 것.
3. 고정 75% 임계값과 무조건 300초 대기가 진짜 위험을 줄이는지 실측. 더 신속한 안전한 진입/명확한 BLOCKED 이유/자원 확보 안내 등 개선 비교. 사용자 허가 없이 다른 프로세스 종료·시스템 설정 변경 금지.
4. 시스템이 실제 저메모리 상황일 때는 안전하게 지연/중단하고, 충분히 여유 있는 상황에서는 불필요한 300초 대기를 하지 않는 양쪽 시험을 필수.

## P1 — 420초 시험 자체의 추가 최적화
1. 깨끗한 반복 실측을 기준으로 `pytest --durations` 상위 25건을 파일·호출 경로·시간으로 다시 분해. R334 재컴파일 원인은 재수정하지 말 것.
2. 반복 subprocess pytest 기동, 격리 Git repo/worktree 생성, 중복 초기화·fixture 구성, 외부 대기·폴링·고정 sleep, 실패한 뒤 반복 실행, 불필요한 데이터 준비 등 **동일한 검증 가치를 유지하면서 줄일 수 있는 원인**을 코드로 증명.
3. 가능한 해결책 비교: 프로세스/fixture 재사용의 격리 안전성, 작업 단위 캐시 유효성, 범위별 테스트 선택(R336), 안전한 부분 병렬화(메모리 실측 조건 충족 시만). 테스트 자체를 단축하려고 timeout 축소/skip/xfail/삭제·결과 하드코딩·mock만으로 대체 금지.
4. 기존 결함 주입 역검증(예전 stale pyc 등) 및 고위험 변경 전체 회귀 게이트 보존.
5. 같은 환경에서 2회 이상 전후 측정(가능할 때), 실행 pytest/검증 게이트/대기 시간과 전체 작업 완료 시간을 **별도** 보고. RAM/commit peak, 통과 항목 수, 실패 탐지력, 불안정성도 함께 확인. 개선이 재현되지 않으면 결과를 부풀리지 말고 원복·원인 기록.

## P2 — 검증 방식의 적재적소 판단
- R336에서 정의할 위험도 기반 시험 선택을 실제 업무 예제에 적용: 문서-only, 국소 버그, 공용 로직, Hook/원장/보안 핵심, 릴리스 등. 전체 회귀가 필요한 시점은 유지.
- 반복 전체 검증이 사용자 지시나 보호 게이트 때문에 필요한 것인지, 단순 중복 호출인지 분리.
- 코드 변경이 없는 테스트 조사 자체가 8분짜리 검증을 무의미하게 반복하지 않도록 계획. 관련 테스트→최종 필요한 전체 회귀 순서로 진행.
- 새로운 테스트 도구/설치·유료 AI 대량 호출 없이 기존 자산 우선 활용.

- 사용자 요구의 개발 품질·정확성 유지. 정책 충돌/승인 오탐 발견 시 기존 Hook을 최소 수정.
- 필요한 테스트·실행 증거, 깔끔한 commit/push 및 단일 R339 보고서. 감사·운영 원장·보호 데이터, 진행 중·승인 대기 내용 삭제 금지.
- 선행 R335~R338의 최종 완료 상태를 변경·정정 없이 확인하고, 기존 사용자의 '모든 작업 완료 후 보고' 지시가 있으면 그 지시를 따른다.
