# R343 — 모든 개발 기술문서/PPT를 근거 기반·환각 억제·동적 확장형으로 생성하도록 Skill·Command 개선

## 사용자 핵심 의도
이번 ICM AgentGo 1.5 아키텍처 PPT 한 건에 맞춰 내용을 하드코딩하지 말 것. 사용자는 개발 중 아키텍처·API·DB·보안·배포·운영·테스트·장애 분석·제안서 등 여러 기술 문서를 반복 생성한다. **설명 문구도 근거에 맞고 정확해야 하며, 사용자 요구/입력 자료/프로젝트 소스에 따라 자료 유형·레이아웃·차트를 동적으로 선택하는 재사용 가능한 문서 제작 체계**가 필요하다.

R342와 중복 새 Agent/Hook/Skill 생성 금지. 기존 `design_ppt`, `arch-auto`, `skill-ppt-pitfalls`, Architect/Designer 및 필요시 다른 design_word/design_pdf 스킬의 공통 규칙을 최소 변경으로 확장. R342 진행을 끊지 않고 R342 완료·검증 후 수행.

## P0 — 환각 방지, 출처·사실 계약
1. 입력(사용자 제공 PPT/기획서/요구사항·소스 코드·설정·DB 스키마·배포 산출물·공식 문서)에서 출처 있는 사실을 추출하고, **사실/해석/권고/가정/미확인**을 구분한다. 모델이 그럴듯하게 추가한 모듈·서버·포트·방향·암호화·규격·성능 수치·수량·배포 특성은 원본 증거 없으면 단정·생성 금지.
2. 원본 표현을 충실히 보존하며 이해도를 높이기 위한 문장 다듬기만 허용. 근거가 부족하면 '미확인'으로 표시하거나 사용자 확인이 필수인 핵심 사항만 질문; 근거 없는 숫자 창작·잘못된 보정 금지.
3. 핵심 문구/표/다이어그램 노드·연결선별 근거 매핑(Slide → claim → source file/section/line/version)과 모순검사. 예: '포트는 9077 하나만 외부 노출', '회사 DB 쓰기 실패 시 HTTP 502', '선택 서버 9078/9080'은 제공 자료 기준으로만 표시; 문서들 간 불일치는 조용히 임의 화해하지 않음.
4. 코드의 구현된 동작 vs 문서의 설계 의도 vs 계획 기능을 구분. 소스 없는 장래 기능을 '이미 제공'이라고 표현 금지. 공식 레퍼런스는 표현·표준의 근거이지 해당 고객/제품 구현 사실의 증거가 아님.
5. 출처·버전·추출시점 표기를 적합한 문서에 유지하고 외부 공개 전 민감 정보·고객 파일·토큰·키 누출 방지. 제공 PPT를 허가 없이 GitHub에 올리지 않는다.

## P1 — 하드코딩 방지, 동적 문서 설계
1. 특정 제품 이름, ICM AgentGo, 9077/9078/9079/9080, 11장, 11개 컴포넌트, 특정 색/도형/3열 카드, 꼭 특정 순서 등을 **엔진의 고정 규칙으로 넣지 않는다**. 이것들은 해당 문서에서 검증된 데이터일 때만 사용.
2. 입력 문서의 목적·대상 독자·기술적 관계·정보량/복잡도·형식을 판단하여 **문서 구조/장수/슬라이드별 텍스트 밀도/다이어그램 종류/표·부록 분리/테마**를 동적으로 결정. 무조건 모든 슬라이드에 그림을 넣거나 텍스트를 한 줄로 축약하지 말 것.
3. 도식화는 의미 중심: 아키텍처 구조=C4 context/container/component, 실행 순서=sequence/activity, 배포=deployment/network, 데이터=DFD/ERD, 보안=trust boundaries, 일정=timeline, 비교=matrix/chart 등. 적절한 도형 종류를 고른 이유와 도식 근거를 검증.
4. 기술 설명 문구에는 주어/행위/조건/결과/예외/단위를 명확히 하고, 용어와 버전을 일관되게 관리. 과도한 '혁신적/완벽한/전면 자동' 같은 근거 없는 마케팅 문구 금지. 고객 발표용·개발자 상세 설계용 톤과 밀도 구분.
5. 재사용 가능한 **단일 SoT 규칙+구성(옵션/스키마/템플릿)**로 구현. 파일/스크립트 별 하드코딩 분기를 양산하지 않고, 기존 명령어·기존 파일 생성 기능·기존 사용자 워크플로우 호환 유지. 불필요한 추가 AI 에이전트 호출 금지.

## P2 — 다른 PPT가 없어도 일반화 검증, 있으면 비교 검증
1. 사용자에게 추가 PPT를 의무 요구하지 말고 **현재 샘플 + 비밀 정보 없는 서로 다른 주제/구성의 합성 문서 최소 3종**(예: 클라우드 API 설계, 배치/DB 데이터 처리, 보안/배포 운영)으로 동일 생성 파이프라인을 검증. 모든 예시에서 포트/DB/AI 공급자/슬라이드 수가 다르도록 하여 특정 제품 내용이 새 문서에 새어 들어가지 않는지 검사.
2. 이후 사용자 제공 다른 PPT가 있으면 추가적인 실제 분포 검증 대상으로 활용; 기존 합성 시험 대체 금지. 다양한 좋은/나쁜 문서에서 스타일을 **그대로 복제**하지 말고 관찰 기반의 일반 원칙만 학습.
3. content QA: source claim 대조, 수치·단위·버전·서비스 명·그림 화살표 의미, 원본 요구 커버리지, 필수/선택 및 비정상 경로. presentation QA: 렌더 화면별 잘림·가독성·텍스트 밀도·폰트/도식 정확성, 편집 가능성.
4. 자동 루브릭 점수를 최종 품질의 유일한 근거로 쓰지 말고 눈으로 확인한 시각 결과·독립 내용 검수 증거를 남김. 새 벤치마크가 기존 R342의 테스트를 중복하지 않도록 재사용.
5. 위험 기반 테스트 선택(R336), 최종 사용자 지시 우선(R335), 전체 성능 검토(R340), 기존 작업 완료 후 최종 보고 원칙 준수.

## 완료 기준
- 여러 기술문서 유형에서 문구 환각·근거 없는 연결선/숫자/성능 주장 0 (검증된 시험 범위에서), 사실/가정 구분 명확
- 서로 다른 입력 문서에 맞춰 레이아웃·다이어그램/장수 동적 선택이 작동하고 ICM 고정 패턴/값 유출 없음
- 기존 Skill·Command의 실제 호출 경로에서 적용됨(규칙 파일만 장식적으로 추가하지 않음)
- 격리된 대표 샘플 전후 결과/실제 렌더 이미지/출처 대조표/검증·회귀 결과를 R343 단일 보고서에 기록
- 고객 원본/승인·운영·감사 자료 보호, 실제 검증된 수정만 안전하게 commit/push, 미검증 시 PARTIAL 기록

**결론: 특정 PPT를 예쁘게 만드는 것이 아니라, 다양한 개발 문서를 근거에 충실하고 거짓 없이, 정확한 문구와 알맞은 그림으로 동적 생성하는 시스템.**
