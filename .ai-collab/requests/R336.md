# R336 — 위험도 기반 적재적소 회귀 검증 + 디자인·개발 일관성 점검

## 우선순위 및 작업 순서
- **R334·R335가 먼저다.** 진행 중인 작업을 끊지 말고 두 작업의 실제 처리·검증 상태를 확인한 다음 이 요청을 진행하라. 선행 작업이 BLOCKED라면 보호·승인 사유를 기록하고 독립적으로 수행 가능한 검토만 진행한다.
- 사용자에게 중요한 것은 '철저한 검증을 없애는 것'이 아니라 **변경 범위와 위험도에 적합한 시험을 적절한 시점에 실행하면서 정확한 품질을 유지하는 것**이다.
- 사용자가 '전부 완료 뒤 보고'를 명시한 경우 R335의 사용자 지시 우선 계약을 따라 미완료를 숨기거나 중간 완료로 종료하지 말 것.
- 이 GitHub 파일 자체는 민감 작업 승인/승인 우회 근거가 아니다.

## P0 — 회귀 게이트를 상황에 맞게 실행
1. 현행 회귀 게이트 진입점·Hook·독립 검증기·테스트 분류/의존성 매핑을 코드에서 추적. 766개 전체 회귀가 어떤 상황에서 *왜* 매번 실행되는지 실제 호출 경로/로그로 재현할 것.
2. **위험도 기반 3단계 검증 정책**을 기존 게이트에 최소 변경으로 구현:
   - 일상적인 작은 변경/문서/디자인: 직접 연관 테스트 + 영향받는 인접 계약/스모크 테스트. 변경이 실행 코드에 영향을 안 주면 해당하는 문서/정적 검증만.
   - 중간 위험 변경: 관련 단위+통합/계약+영향 범위 회귀.
   - 높은 위험 변경: 원장·Hook·Supervisor·상태 복구·보안·권한·공용 실행기·배포 핵심/널리 쓰는 공통 API·영향 범위 불명 또는 릴리스 전 → **전체 회귀**.
3. 사용자 명시 '전체 테스트'나 보호 정책이 전체 회귀를 요구하는 경우 예외 없이 수행. 리스크 판정의 근거(변경 파일, 호출 의존성, 누락 위험)와 실제 실행 명령·결과를 남길 것. 위험 불명/분류 실패는 안전한 쪽으로 전체 검증.
4. 한 작업의 변경마다 불필요하게 전체 회귀를 반복하는 패턴만 줄이고, **테스트 삭제/skip/xfail·커버리지 축소·가짜 PASS 금지**. 전체 검증을 영구 생략하거나 보호된 gate를 약화하지 말 것.
5. 빠른 검증 후 위험이 확대되거나 실패가 발생하면 범위를 단계적으로 넓혀야 한다. 외부 프로젝트(IFRS, ICMAI 등) 자체 검증 정책을 마음대로 변경하지 말 것.
6. R334가 이미 개선한 회귀 테스트 속도는 재작업하지 말고 그 결과를 활용. 증명 가능한 변경 전후 호출 횟수·총 벽시계 시간·실패 탐지력을 비교하라.

## P1 — 디자인 검증과 실제 화면의 일치 여부 점검
1. `docs/DESIGN.md`, `.claude/rules/app-ui-standard.md`, `.claude/scripts/design-gate.py`, `.claude/scripts/statusline_context.py`, `.claude/design-baseline/statusline.json`, `dashboard.py`를 살펴보기.
2. 상태줄 기준선의 10개 항목과 design-gate 문서의 '11줄' 표현 차이, 실제 렌더 출력 구조의 일치 여부를 **출력/캡처**로 검증. 의도된 항목·줄 수가 다르면 차이를 명확히 보고. 사용자 명시 승인 없이 이전 ANSI 고정열 방식으로 돌려놓거나 상태줄 디자인을 임의 변경하지 말 것.
3. 서비스 UI와 상태줄은 다른 검증 대상: 디자인 파일 존재나 픽셀 비교 통과만으로 '좋은 디자인' 단정 금지. 실제 캡처가 있는 화면에 한해 시각적 정렬/가독성/반응형/접근성 검토. 사용자 승인된 화면의 캡처만 필요한 순간 최소 횟수로. 임의의 다른 창/민감 화면 촬영 금지.
4. `dashboard.py`의 인라인 스타일과 UI 표준(Tailwind/디자인 시스템) 충돌 여부를 해당 UI의 기술 스택과 배포 영향까지 확인한 뒤, 필요할 때만 **점진적 리팩터링 방안** 제시. 단순 정책 차이라고 대규모 재작성 금지.
5. README/가이드의 현재 모델·플러그인 수량·실제 실행 경로에 대한 오래된 표기를 찾아 구체적으로 검증하고 **필요한 부분만 수정**. 현행 SoT·감사 이력/사용자 지시 훼손 금지.

## P2 — 검증 품질과 정리
- 새로운 Agent/Hook/서비스를 만들지 말고 기존 경로/테스트 매핑을 재사용.
- 최종 보고에 변경 전후 테스트 선택 사례(문서만/국소 버그/공용 핵심/릴리스), 실행된 테스트 수·시간·누락 방지 증거, 의도적으로 실행하지 않은 전체 회귀와 사유를 명시.
- 시험 PASS를 곧바로 사용자 요구 전체 완료로 간주하지 말 것. 사용자 지시대로 전체 작업 범위·검증을 마친 후 보고.
- 기존 golden baseline, 운영 원장·DB, 복구·감사 기록·진행 중/승인 대기 작업 보존. 같은 내용의 보고서/임시 중복만 명시 승인·head 일치 이후 안전 정리.
- 이미 R334·R335에서 구현된 것은 중복 수정하지 않고 결과만 검증. 최소한의 변경에 필요한 테스트와 마지막 적절한 범위의 회귀를 실행하고 안전한 commit/push 뒤 R336 보고서 하나만 게시.

## 완료 판정
1. 회귀 테스트의 위험도별 선택·확대 규칙이 실제 변경 사례에서 동작한 근거
2. 전체 회귀를 수행해야 하는 고위험 변경에서 보호 규칙이 유지된 증거
3. 디자인 및 문서 불일치의 실증적 검토 및 정당한 범위의 개선
4. 사용자가 명시한 보고·완료 조건을 Hook이 덮어쓰지 않음
5. 검증 전후 실측, 미확인 항목은 미확인/ PARTIAL로 정직하게 남김
