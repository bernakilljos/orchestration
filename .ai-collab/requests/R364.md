# R364 — 사용자 지시 이행 신뢰성 심층 감사, 상태머신·교착·복구·완료 판정 결함의 실증 수정

## 사용자 최상위 실행 원칙 — 모든 정상 작업에 적용 (2026-11-23)

사용자의 직접 지시: "다른 것도 내가 지시하면 뭐든 지시를 해결해." 특정 PowerShell 사례만이 아니라 모든 개인용 개발·운영 작업에 적용한다.

1. 명확한 사용자 지시를 받으면 기대하는 실제 종료 상태를 확인하고, 필요한 최소 사전 점검 후 **가능한 조치는 즉시 실행**한다. 설명·보고서·전수조사가 실제 문제 해결을 대체하거나 불필요하게 지연시키지 않도록 한다.
2. 이미 사용자 지시와 기존 권한 범위로 실행 가능한 코드 수정, 대상 테스트, 일반 Git push, 승인된 환경 전파, 비파괴 오류 복구는 중복 질문 없이 실제로 수행하고 결과를 검증한다. 실제 도구에 접근할 수 없거나 필수 입력이 없는 경우만 한 번 명확히 설명한다.
3. 보안상 고위험 작업(Windows 관리자 권한/UAC, 보호 경로의 삭제, 미승인 파괴 작업 등)은 기존 승인과 OS 인증을 무단 우회하지 않는다. 단, **고위험 단계 하나가 막혔다고 나머지 합법적이고 독립적인 작업까지 중지하거나 같은 승인 안내를 반복하는 것은 결함**이다.
4. 하나의 사용자 목표에 대해 작업을 지나치게 쪼개거나 명령을 불필요하게 바꿔 새 승인 ID를 만들지 않는다. 현재 승인 요청은 실제 범위와 유효성을 확인해 고정하고, 상태 변화가 없으면 같은 설명을 여러 번 보내지 않는다. 정식 위험 승인 없이 실행 가능한 별도 조치는 먼저 완료한다.
5. 수정 후에는 **사용자가 원한 실제 결과**를 확인한다. rc=0, 문서 등록, 단위 테스트 PASS, commit/push 완료만으로 목표 완료 처리하지 않는다. 기대 결과가 없으면 DONE이 아닌 BLOCKED/PARTIAL과 한 가지 다음 행동을 기록한다.
6. 단일 현장 오류는 '최소 진단→직접 해결→사후 확인'을 우선하고, 12종·24종 시뮬레이션, 대규모 회귀, 문서/전파는 직접 해결의 선행 조건으로 만들지 않는다. 단, 공통 구조 결함이 확인되면 직접 해결과 분리해 정밀 재발 방지 테스트를 수행한다.
7. 이 원칙이 실제로 모든 작업 유형에 적용되는지 일반 파일 작업, 코드 버그, Git/전파, 관리자 승인 대기, 테스트 실패, 도구 오류 등 격리 E2E 사례를 통해 검증하고, 문제가 재현되면 관련 정본 로직을 수정한다. 기존 사용자 상태와 감사 데이터를 보존한다.

**수용 기준:** 사용자 요청을 실제로 완료한 근거 또는 불가능한 외부 인증/권한 사유를 명확히 제시하고, 같은 지시를 여러 번 반복하게 만드는 작업 교착을 줄일 것. 업무 완료와 위험 작업 승인 절차는 서로 분리한다.

## 목적 및 R363과의 역할 분리
R363은 Windows System32의 확장자 없는 powershell 파일 문제와 승인 교체 교착을 해결하는 구체적 재현·수정이다. R364는 그 사례를 시드로 전체 개인용 Claude CLI 오케스트레이션에서 '명확한 사용자 지시가 있었는데 작업은 미완료인 채 승인/도구/검증/보고만 반복하는' 공통 결함을 재현·수정하는 수평적 심층 감사다. R363의 같은 조사·시험·문서를 복제하지 말고 하나의 공통 fixture, 코드·테스트·증거를 재사용하라. 이번 요청은 사용자 명시 지시이므로 가능한 정상 개발/검증/커밋/Push는 수행하되 위험한 권한 상승은 별도 인증 경계를 준수한다.

- 선행 R363은 12개 격리 E2E 및 직접 삭제 여부 확인을 지시했지만 현재 GitHub에는 R363 보고서·코드 수정 증거 없음. 등록한 지시문을 완료 성과로 간주 금지.

## P0 A. 실행/승인/보고 실제 상태머신과 단일 진실원(Source of Truth) 감사
1. 관련 진입점과 데이터 계약을 파일/함수/스토리지 단위로 열거: UserPromptSubmit → task planning/goal id → tool dispatch/PreToolUse → security approval request/withdraw/consume → Windows UAC/실제 도구 → PostToolUse → 회귀 테스트 → 커밋/push/전파 → report/review → Stop/restart/resume. 실제 연결이 없는 기능을 연결된 것으로 가정하지 말 것.
2. 한 사용자 목표에 대해 task_goal_id, operation_id, command_fingerprint(scope 포함), approval_request_id, current_state, next_action, last_error, blocker, evidence, updated_at을 어떻게 연계하는지 조사. 기존 스키마·상태가 충분하면 재사용, 새 DB·상주 Hook·중복 큐를 함부로 만들지 말 것. 각 ID 목적을 분리하되 같은 작업을 무한 신규 생성하지 않도록 한다.
3. 정상 전이 예: RECEIVED→PLANNED→PREFLIGHT→RUNNING→VERIFYING→DONE; 조건부 WAITING_APPROVAL/WAITING_UAC/BLOCKED/FAILED/RESUMABLE. 현재 코드의 실제 상태 이름과 매핑. UAC 또는 수동 승인 대기와 실제 사용자 목표 완료를 혼동하지 말 것.
4. 핵심 불변조건: 위험 명령 미승인 실행 0; 승인 뒤 스크립트/대상 변경 실행 0; 같은 scope 대기 승인 중복 생성 0; 1개 사용자 목표를 DONE으로 기록하면 실제 사후조건 증거 필수; BLOCKED가 장시간 반복되더라도 무의미한 모델 호출/메시지 증식 0; 재개 시 이미 완료된 비파괴 단계 재실행 최소; 외부 확인 없이 UAC 승인했다고 간주 0.

## P0 B. 조합·장애주입 시뮬레이션: 작은 격리 환경에서 재현 → 수정 → 재실행
Windows/PowerShell·Git Bash·Python 호출을 실제 hook 실행기에 가능한 가깝게 포함. 최소 24개 검증 케이스를 범주별로 설계하고 시험 코드로 자동 실행. 표에는 사례ID, 시작상태, 사용자 메시지(의도), 명령범위 SHA, 승인 DB 상태, 실제 실행 결과, 기대 상태, 관측 상태, 전후 테스트가 들어가야 한다.
- 승인 8: 신규 승인대기, 동일 지문 중복, 스크립트 내용 변경, 작업 폴더/대상 변경, 대기 취소 후 새 명령, 승인 1회 소비/재사용 불가, 만료/거절, 사용자 문구 재촉(정식 승인 없음).
- 도구/환경 6: Bash→PowerShell 경로 변환, System32 명령 shadowing, 비관리자 access denied, 정상 UAC 수락/취소의 테스트 더블, subprocess timeout/kill, rc=0이나 효과 없음.
- 라이프사이클 6: 반복 지시 2회/5회, 실행 중 다른 우선순위 작업, 게이트와 병렬 회귀 충돌, push 실패 후 재개, Claude 세션 재시작/중단, report PARTIAL 후 다시 실제 작업으로 재개.
- 보안/완료 4: symlink/junction·시스템 보호 파일 보존, 승인 DB 위조/Hook 우회 차단, 정상 변경 후 회귀 유지, 결과 사후 검증 실패 시 DONE 금지.
실제 C:\Windows\System32 수정/파일 삭제는 절대 테스트에서 수행하지 않는다. 모든 삭제는 가짜 파일 격리 임시 디렉터리에서만. 원본 로그에서 미확인 항목은 가설로 표기, 테스트 결과를 운영 환경 성공으로 과장하지 말 것.

## P0 C. 재현된 결함의 정본 코드 수정 (문서만 쓰고 종료 금지)
1. 먼저 baseline FAIL을 확인. 실패 원인을 결함 유형별로 분류: 중복 승인/불필요한 명령 변경, 승인 대기 중 목표 유실, 상태 전이 불일치, 실패인데 DONE 기록, 반복 안내, 낮은 위험 작업까지 연쇄 정지, 특정 셸에서 경로 파손, 회귀 게이트/커밋 대기가 대화 요청을 굶기는 현상.
2. 실제 고장 난 정본 코드만 최소 패치하고 시험 PASS. 동일 지문 pending 확인을 새 요청 생성 전에 수행하되, **서로 다른 명령·스크립트 해시·권한 범위에 동일 승인을 재사용하지 말 것**. 이미 정상인 승인 보안 게이트 전체를 끄거나 화이트리스트로 구멍내지 말 것.
3. 작업 완료는 사용자 목표에 대한 사후조건 판정으로만 인정. 예: 대상 파일 삭제=Test-Path false+정상 서명 PowerShell 호출+앱 선택 팝업 미발생. 만약 Windows 인증이 필요하면 관리자 단계는 정확히 WAITING_UAC/BLOCKED로 남기고, 이미 끝난 다른 안전한 단계는 별도 PASS로 표기.
4. 반복 사용자 지시가 들어오면 장황한 동일 승인 답변 대신 진행상태와 변경된 사실을 한 번만 전달하고, 다른 안전한 행동을 실행한다. 사용자 의도와 OS/Hook 승인 분리. **UAC 또는 정식 위험 승인 요청은 사용자가 결정해야 할 수 있으므로 Claude가 대신 클릭/등록/변조하거나 일반 텍스트 지시를 고위험 승인으로 자동 승격하지 않는다**.
5. 명령 생성 전에 사용자 목표와 필요한 변경을 확정해 스크립트 파일·SHA·작업 폴더·대상 위치를 가능한 한 고정. 변화가 불가피하면 사유/새 범위가 사용자에게 이해 가능하도록 한 번 보고. 새로운 appr ID 자체를 버그라고 간주하지 않되 불필요한 명령 재작성 원인을 고친다.

## P1 D. 폭넓은 영향 및 성능 검증
- 승인 이외에도 운영 배포, Git push, 프로젝트 sync/merge, 에이전트 실행과 Supervisor, CI, 상태줄, 보고서 발행에서 유사한 WAITING→반복 오류 패턴이 있는지 실제 호출 그래프 기반 조사. 의미 없는 새 Hook, 스케줄러, 플러그인 추가 금지.
- 기존 Windows CI/Test Matrix와 Security Scan 실제 job 재확인. 변경 부분의 단위/통합 시험 우선, 최종 preflight 후 고비용 전체 게이트 1회 원칙. 오류가 발생하면 수정 후 필요한 회귀만 재실행하며 같은 10분짜리 게이트를 여러 번 불필요 재실행 금지.
- 동등 환경에서 wall time, 재시도 횟수, 승인 요청 발급 수, 토큰/CPU/RAM, 사용자 반복 지시 횟수, 목표 완료 비율을 가능한 범위에서 before/after 측정. 표본 없으면 NOT_MEASURED.
- 개인용 운영 환경과 배포 대상의 활성 정본 해시·설정 경로를 확인. 정상 안전 작업은 지체 없이 commit/push/검증/필요 대상 전파; 다른 워커의 미커밋 변경·운영 DB·로그·감사 데이터는 보호.
