# R353 — 사용자가 이미 지시한 전파·배포·일반 Push의 반복 /approve 차단 근본 해결 및 실제 대상까지 정책 전파

## 긴급 사용자 의사 결정 (이번 요청으로 명확)
- 개인 **1인 운영자**가 실제로 명시한 **비파괴적인 정규 개발·Git push·동기화·전파·배포 작업**은 매번 `/approve appr-...`를 입력시키지 말 것. 사용자가 '지시'했는데도 실행할 때마다 승인 요청을 되풀이하는 것은 사용자의 요구 미충족이다.
- **허가되지 않은 고위험 파괴 행동**(강제 push·기록 재작성·원격 삭제·예상치 못한 운영 데이터 제거/파괴적 DB 변경·권한 변경·기밀 유출·명시 범위를 벗어난 새로운 환경에 배포)은 이 요청으로 자동 허가된 것이 아니다. 이들은 기존 보호를 유지. 1인 사용자라는 이유만으로 모두 자동 허가하는 우회는 금지.
- 사용자가 앞서 제외한 **비밀정보 저장소 파일 권한 강화**는 이번 범위에서 제외. 기존 비밀정보 보호는 유지.
- 승인 요청 ID `appr-f5e8e79c35e5`만 특례로 하드코딩 금지. 대상 환경 전체에 재발하지 않도록 **원인→정책 정본→설치/전파→실행 경로** 검증.
- 사용자가 명시 승인한 Git push/전파 작업을 Hook이 잘못 차단하는 문제는 **현행 진행 중인 작업과 병행 시 위험한 쓰기를 피하면서 우선순위 높게** 개선.

## 현재 GitHub에서 직접 확인한 불일치·경로 (구조적 증거, 실제 승인 ID의 원인은 로컬 DB에서 확인 전 미확정)
- `.claude/scripts/approval-gate.py`에서 `is_plain_push`는 제한된 형태의 일반 `git push [origin ...]`만 별도 승인 없이 처리한다. 반면 위험 패턴에는 `scp`, `docker push`, `kubectl`, `vercel --prod`, `netlify/firebase deploy`, `terraform apply`, 사용자 전역 `~/.claude/commands|skills|agents|settings` 파일 갱신 등을 별도 카테고리로 분류한다.
- `.claude/hooks/tool/approval_gate_detect.py`는 전처리·스크립트 내용 검사·대상 폴더/해시를 별도로 확인한다. 일반 push라도 명령 연결, shell wrapper, cd/git -C, pipe, PowerShell, 변수·스크립트 경유 등 실사용 경로에서 예외 판정과 충돌할 가능성.
- `.claude/hooks/prompt/user_approval.py`는 `/approve appr-...` 형식의 실제 사용자 메시지만 승인으로 기록하며, `approval-gate.py`는 30분/1회 소비 방식. 이미 사용자 명시 지시로 허가된 범위에 매번 이를 요구한다면 중복 승인이다.
- `.claude/rules/approval-gate-rules.md`에는 구식 예제인 `approval-gate.py approve` 등 실행 경로가 남아 있고 실제 CLI 제약과 불일치 가능. `.claude/hooks/hook-04-pre-deploy.md`에는 PROD Team Lead 수동 승인 같은 **다중 사용자 가정**이 남아 있다. 실제 실행되는 문서인지 먼저 추적하고 관련되면 1인 운영 사용자 정책과 정합성 수정.
- `.claude/rules/sync-workflow.md`, `.claude/scripts/sync-plugins.py`, `.claude/hooks/propagate-rule-change.sh`, `plugins/` SoT 및 대상 프로젝트 설치/배포 경로에서 **정책이 원본에서 실사용 사본까지 실제로 도달하는지** 확인. 이미 R351에서 sync 덮어쓰기 보호를 수정했으므로 이를 무시하고 강제 sync로 사용자의 수정본 삭제 금지.

## P0 — 실제 요청 원인을 확정 (재현 없는 보안 완화 금지)
1. 실제 사용자 로컬의 승인 요청 `appr-f5e8e79c35e5`의 원본 명령, 실행 폴더, 카테고리, 위험 상세, 생성 시각, 해당 시점 정책·Hook 버전/해시를 **승인 DB와 감사 로그에서 읽기 전용으로 조사**. GitHub에는 승인 DB가 없을 수 있으므로 접근 불가면 **미확인**으로 기록하고 코드의 일반적 원인과 구분.
2. `CLI 명령→Hook dispatcher→승인 위험 분류→스크립트·하위 명령 검사→명시 사용자 지시 범위 판정→실행 환경 정본→전파 사본` 전체 호출 그래프를 실제 코드/설정/로그로 확인. 일반 git push, 배포/동기화, 사용자 지시가 없는 위험 작업을 반드시 구분.
3. 원본·설치본·전파 대상·재시작 후 활성 Hook의 버전/해시와 차이를 나열해 **'소스 수정은 됐지만 대상에는 구버전'** 상태와 '정책 분류 오류'를 서로 구별.

## P1 — 정책 정본과 동적 허가 범위
1. 작업별 사용자의 **명시된 의도·승인 범위·대상 프로젝트/환경/원격·명령이 실제로 하는 비파괴 동작**을 확인할 수 있는 기존 ledger/authorization evidence를 사용한다. 요청을 받았다는 사실만으로 파괴 작업까지 승인했다고 확장하지 말 것.
2. 기존 정규 작업(일반 origin push, 비파괴적인 설치 사본 동기화, 기존에 사용자 지시한 확정 대상에 대한 일상 전파·배포)은 **동일한 사용자 지시 범위 내에서 재승인 반복 방지**. 그 작업의 명령 표기/경로/전달 방식(예: script wrapper, Git Bash, PowerShell, pipe)을 바꾸어도 실질 동작이 같으면 오탐 없어야 한다.
3. 구체적 승인 ID/특정 프로젝트명/포트/명령 문자열만 whitelist로 추가하는 땜질 금지. **정규화한 명령 의미와 대상 효과·실행 범위/부작용**을 기반으로 판정. 해석 불가/고위험/범위 변경은 별도 승인 필요를 명확히 드러내고 우회하지 말 것.
4. `approval-gate.py`, `approval_gate_detect.py`, 전파 스크립트, 문서 Rule/Skill/Command 간 복제된 판단을 공통 정본에 수렴하되 최소 변경. 중복 Agent/Hook/DB 추가 금지. 보호 목적과 일반 편의 규칙을 구분하고 필요 없는 '팀장 승인' 조직용 가정 제거.
5. 사용자 허가의 대상 변경(다른 remote/branch/서버/운영 데이터)이나 위험한 동작으로 확대될 때는 이전 승인을 무조건 재사용하지 않는다. 무승인 범위를 넓히는 대신 **정상 경로의 불필요한 중복 승인만 없애는 것**이 목표.

## P1 — 실제 '전파 완료' 증명
1. 원본 SoT에서 관련 스킬/명령/Hook/설정/배포 사본의 연결을 정리하고, 설치 경로·실행 경로별 활성 버전/해시 비교. GitHub main 갱신만으로 실환경 동작을 확인했다고 주장 금지.
2. 사용자 운영 파일, 전파 대상 프로젝트, 글로벌 ~/.claude에 이미 있는 내용의 무단 덮어쓰기·파괴 금지. R351 sync 보호의 drift/force 계약을 지키면서 허가된 대상만 원자적으로 동기화하고 결과를 검증.
3. Git Push 허용과 배포·전파 허용은 **각각 다른 부작용**임을 고려해 동작별 테스트. 이미 명시적으로 허가한 정규 대상만 무중복 승인; 추가 대상은 사용자 의사 확인.
4. 필요 시 열린 Claude CLI 세션/Hook 프로세스가 새 버전을 실제 로드하는지 확인하여, 재시작이 필요한 경우만 명시. 재시작 없이 적용 확인이 가능하면 불필요하게 세션 종료 요구 금지.

## P2 — 실패/성공 주입 테스트
- 통과해야 할 사례: 허가된 기존 repo 일반 push, 출력 리다이렉션·파이프 변형, 경로가 확정되는 script-wrapper, 승인된 기존 배포 대상의 정규 전파, 관련 문서/설정만 갱신, script/파일 이름에 위험 단어가 포함된 단순 git add/grep, 이미 유효한 같은 범위 승인 재사용.
- 막아야 할 사례: force push, 타 remote/미지 대상, 원격 브랜치 삭제, 예상치 못한 프로덕션/DB 변경, 악의적 명령 연결, 승인 이후 실행 파일/대상 해시 변경, 사용자 지시 없는 publish/deploy, 허가 범위 외 영구 전역 설정 수정.
- 불확실/환경 제약: 실제 승인 DB에 접근할 수 없으면 원인 미확정, 실제 전파 환경에서 테스트 못하면 '전파 미검증'. 정상 경로와 고위험 우회 경로의 positive/negative fixture 각각 실행.
- `approved 범위→명령 실행→Hook 판정→전파 파일 및 hash→실제 active behavior`의 증거 연결, 테스트 통과율·거짓 승인 차단 건수·오탐 건수·재승인 요구 건수·wall time 측정.
- 공식 Claude Code Hooks https://code.claude.com/docs/en/hooks , Anthropic Permissions https://code.claude.com/docs/en/permissions , Git hooks https://git-scm.com/docs/githooks 의 실제 문서 본문/적용 버전을 확인하고 구현과 대조. 정책/안전 완화가 아닌 사용자가 지시한 명시 범위의 중복 승인 개선.
