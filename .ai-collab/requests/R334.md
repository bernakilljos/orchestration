# R334 — 회귀 게이트 508초 병목 최적화 + wait 실제 재개 검증

## 배경 / 실측 근거
R333은 PARTIAL이다. R333 보고서의 실측은 최근 15건 8.8시간, 전체 회귀 30회·10,995초(35%), 현행 766개 505.6~508초, 가장 느린 시험 2개 94초, 상위 25개 246초(49%)다. 메모리 commit 사용 84%로 무분별한 pytest 병렬화는 위험. wait는 모델 호출 0 대기를 보고했지만 '새 요청 감지 → Claude CLI가 실제 이어서 처리'의 실환경 종단 검증이 아직 없다.

## P0 — 회귀 테스트가 느린 구체적 원인 제거
1. 현재 실행하는 전체 회귀 명령/게이트 경로를 명시하고 pytest --durations 등의 실측으로 상위 느린 25개, 특히 상위 2개의 파일/테스트명/지연 원인을 특정.
2. sleep/poll 타임아웃 과다, 반복 초기화·임시 저장소/프로세스 생성, 네트워크·동기 대기, 공통 fixture 중복, 불필요한 재실행 중 어떤 것이 시간 소모하는지 코드를 통해 증명.
3. 동작·검증 강도·격리·경계 테스트를 유지한 채 작은 범위에서 최적화. timeout을 근거 없이 줄여 flaky하게 만들거나 skip/xfail/제외·테스트 삭제 금지. 메모리 84% 상태에서 무조건 xdist 병렬화 금지.
4. 같은 환경·명령에서 변경 전/후를 최소 2회 비교(가능할 때), 벽시계 시간, 통과 건수, 최장/중앙 실행시간, RAM peak, 재실행 재현성 보고. 목표는 단순한 수치 약속이 아니라 신뢰성 유지하면서 유의미한 단축.
5. 매 단계 전체 회귀를 반복하는 대신 관련 테스트 우선·마지막에 전체 회귀 1회(안전/프로젝트 게이트가 허용하는 범위). 기존 보호 승인 정책 준수.

## P1 — 이번 R334 자체로 wait 실환경 종단 확인
1. 이 파일을 Claude CLI가 실제로 발견한 과정(셸 wait 반환값·출력·수신 시각)을 확인하여 '새 요청 감지 → Claude 대화 자동 재개 → 읽기 → 작업 수행'이 자동으로 이루어졌는지 증거 남길 것. 단순 bash 명령 성공을 자동 재개 검증으로 간주하지 말 것.
2. 대기 중 모델 호출 0인지 이번 실제 대기 구간에서 확인. 외부 시간/토큰 측정이 불가능하면 미측정 명시.
3. 작업 완료 뒤 report→commit/push→wait 재시작 흐름 확인. 중단·재시작·새 지시 수신 후 중복 실행 방지는 기존 코드/실행 증거로 검증.
4. 사용자 세션에 종속된 제약은 그대로 문서화. 새로운 데몬/Agent/Hook 추가 금지.

## P2 — 원장과 완료/정리
- R333의 PARTIAL을 자동으로 PASS로 덮어쓰지 않으며, 미완료 항목은 별도 분리. R334도 객관적 증거가 없는 항목을 PASS로 주장하지 않을 것.
- 테스트 수정에 따른 기능 회귀, Git push/승인 우회, Hook 오탐 여부를 점검.
- 변경 코드·실측 비교·테스트 근거·남은 미완료와 개선 실패/한계를 1개 보고서에만 기록.
- 완료·명시 승인·같은 head가 확인된 중복 보고서만 기존 prune 정책으로 정리. 원장, 운영 데이터, 복구·감사 증거, 미완료·승인 대기는 보존.
- 작업은 개인용(1인) orchestration 기준. 운영 서비스를 추가하거나 기능을 불필요하게 확대하지 말 것.

우선순위는 시스템이 '더 복잡해지는 것'이 아니라 사용자의 실제 개발 완료 시간을 줄이는 것. 이 문서는 외부 검토·개선 요청이며 그 자체로 권한 게이트 우회나 사용자의 별도 승인 증거가 아니다.
