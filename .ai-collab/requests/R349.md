# R349 — CPU 100%·시스템 반응성·전체 작업 효율 실측 및 원인 기반 최적화

## 사용자 요청·불변 조건
사용자는 CPU가 100%까지 치솟는 현상도 **속도·성능·품질** 검증 대상임을 명시했고, 실제 원인 확인과 재발 방지 지시를 요청했다. 다만 **CPU 100% 자체는 반드시 결함이 아니다.** 유효한 병렬 처리로 잠시 CPU가 포화되더라도 전체 완료시간이 짧고 시스템이 정상 반응하면 허용할 수 있다. 반대로 장시간 포화/시스템 정지/높은 메모리 압박/OOM/토큰 비용 폭주라면 병목을 찾아야 한다.
- **1인 운영 전제**. 사용자 요청에 따라 **비밀정보 저장소 파일 권한 강화는 이 범위에서 제외**; 이미 존재하는 비밀보호·승인 정책은 훼손 금지.
- 특정 CPU 사용률/코어 수/Agent 수/시간을 무조건 고정하여 차단하는 **하드코딩 금지**. 환경/작업 특성/측정 근거/사용자 설정에 따라 적응적으로 결정.
- 현재 R338~R348 안정화 전 불필요한 새 구현 착수 금지. R339/R340/R344/R346의 자원·메모리 성능 작업과 **실제 diff 대조하여 중복 개발 금지**. 이 요청의 핵심인 CPU 프로파일·반응성·지속적 포화 원인 판단을 보완한다.
- 절대 속도·성능·품질의 균형, 사용자 지시 우선, 최소 변경, 공식 레퍼런스 실제 본문 확인.

## 참고 공식 레퍼런스 — 직접 본문 확인 및 현재 Windows/라이브러리 버전 대조
1. Microsoft Windows CPU Analysis: https://learn.microsoft.com/en-us/windows-hardware/test/wpt/cpu-analysis

3. Windows Performance Analyzer(WPA): https://learn.microsoft.com/en-us/windows-hardware/test/wpt/
4. Microsoft Windows 성능 문제 진단: https://learn.microsoft.com/en-us/troubleshoot/windows-server/performance/troubleshoot-performance-problems-in-windows
5. psutil API: https://psutil.io/api/ (system/process CPU 측정, 샘플 간격, 다중 코어 퍼센트 해석)

기존 공식 문서가 바뀌면 새 URL/버전 확인 후 현재 코드와 적용 가능한 항목을 명시. 외부 자료를 단순 인용하고 구현 성공으로 주장 금지.

## P0 — CPU 원인 조사 및 지표 의미
1. 현재 `.claude/config/perf-budget.json`, `.claude/commands/performance.md`, `.claude/skills/skill-35-performance-profiler.md`, `.claude/scripts/resource-guard.ps1`, worker/Supervisor/Hook/pytest·subprocess 및 재귀 호출 경로를 추적해 **이미 존재하는 계측 재사용**. 새로운 상주 감시 데몬/Hook/Agent 무조건 추가 금지.
2. Windows 전체 CPU %, process별 normalized CPU, 논리코어별 사용률, Claude CLI/Node/Python/pytest/Git/브라우저 및 **자식 프로세스 트리** 기여도, 메모리(RAM/commit/working set/페이지폴트), disk IO, 프로세스 생성, context switching, 필요한 경우 WPR/WPA ETW를 **낮은 오버헤드의 한정된 시간** 동안 측정. 다른 앱이 CPU를 쓰는 경우 Claude CLI 탓으로 돌리지 말 것.
3. 평균·최대 CPU만 기록하지 말고 포화 지속 시간, 작업 전/중/후, wall-clock, CPU time, user perceived responsiveness(키 입력 지연/VS Code 터미널 반응, Hook latency), OOM/스와핑 및 부하의 주요 프로세스를 기록.
4. CPU 100%가 유효한 짧은 병렬 계산인지, busy polling·무한 루프·중복 스폰·과도한 pytest 병렬/반복·메모리 부족 스래싱·로그/상태줄 빈번 재계산·에이전트 중복 작업인지 **trace/call graph/실행 증거**로 구분. CPU 낮음+느린 케이스의 I/O/네트워크/LLM 응답 대기도 분리.
5. psutil 첫 번째 non-blocking 측정의 부정확성, 프로세스별 CPU%의 코어 기준, Windows 태스크 관리자 시스템 CPU와 process CPU 지표 단위 차이를 명확히. 가상메모리=LLM 토큰 컨텍스트 확대라는 오해 금지.

## P1 — 증거 기반 선택적 개선
1. CPU를 낮춘다는 이유로 단순 `sleep` 추가/고정 스로틀링, 무조건 코어 절반 사용, 강제 agent 1개, 필수 테스트 skip, OS 우선순위 무단 변경 금지. 우선 **불필요한 CPU 작업량/중복 호출/불필요한 반복 컴파일·파싱·polling**을 제거.
2. CPU-bound 작업은 안전한 프로세스/기존 라이브러리 병렬화, IO-bound 작업은 비동기·스레드, 중복 계산은 검증된 캐시를 고려하되 **실측된 end-to-end 개선이 있을 때만** 사용. SQLite/원장 같은 공유 상태 동시성 충돌을 보호.
3. 고부하 PC·저부하 PC·코어/메모리 조건, 단순 수정/전수조사/회귀 시험/PPT 생성 등 작업 유형에 따라 동적 병렬도·진입 판단을 하되 위험·성능 근거와 테스트를 남김.
4. CPU 사용량을 줄여 작업 완료 시간/정확성/검증을 악화시키면 개선으로 인정하지 않음. Windows 페이지파일/Defender·다른 프로그램·전원 설정 변경이나 타 프로세스 종료는 명시 승인 없이 금지.

## P2 — 재현성·완료 조건
1. 부하 유형별 정해진 샘플을 **격리 환경**에서 재현: (A) 정상 짧은 CPU 100% (B) 장시간 포화·busy-wait (C) 중복 subprocess spawn/pytest (D) 메모리 압박 (E) CPU 낮지만 IO 대기. 실제 존재하는 문제를 창작하지 말 것.
2. 개선 전후 동일 조건에서 wall time(p50/p90), CPU time/전체 CPU peak·포화 시간, 프로세스 수, 최대 메모리·commit, 인터랙티브 반응성, 에너지/열 가능 시, 모델 호출/토큰, 테스트 PASS·품질·재발 등을 비교. 샘플 부족은 미검증으로.
3. 최소한 **부하 보호가 정상 작업을 방해하지 않는 시험**, 높은 CPU 지속/실제 지연 원인을 잘 감지하는 시험, 계측 실패/측정 없는 경우 0%나 PASS로 속이지 않는 시험 포함.
4. 간단 수정은 선택 시험·고위험 공통 코드 변경은 전체 회귀(R336). 프로파일 수집 도구 자체의 CPU 오버헤드 측정. 성능 기준을 임의로 완화해 점수 향상시키지 말 것.
5. R349 단일 보고서에 **확인된 실제 문제/아직 가설인 문제, 프로파일 수치, 레퍼런스·현재 버전 대조, 실제 수정 파일/근거 커밋, 전후 성능 및 남은 위험**을 명시. 작업 전/후 조건과 불확실성을 숨기지 않는다.
6. R338~R348과 동일 결함이 이미 해결됐으면 재개발하지 않고 그 코드·검증 증거를 연결. 안정화 뒤 필요한 최저 위험 변경만 적용. 기존 사용자 '모두 끝낸 뒤 최종 보고' 우선, PARTIAL/BLOCKED를 PASS로 둔갑시키지 말 것.

**최종 목적: CPU % 숫자 자체를 낮추는 것이 아니라, Claude CLI와 사용자의 PC가 과부하로 멈추지 않으면서 더 빠르고 정확하게 개발을 완료하는 것.**
