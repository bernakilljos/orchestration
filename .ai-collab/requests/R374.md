# R374 — 사용자 승인한 복사본 두 폴더 정리, 같은 승인 반복 요구 방지

## 사용자 목표와 근거
사용자: "이거 했는데 왜 또 문제야. 지시문 다시 작성해... powershell처럼 이것도 사용자가 먼저 해야 하잖아."
Claude CLI가 rm 및 Python 삭제를 시도했으나 승인 게이트가 차단했다고 보고. 두 번째 요청은 취소했고 기존 요청 ID는 appr-7ec778ec76e6 한 건이라고 보고.
정확한 대상은 C:\자료\03.PJT\_ref_github (약 2.0GB), C:\자료\03.PJT\C.ICM_Agent_Go\_ref_push (약 1.2GB).
"7개 저장소가 GitHub와 동일"하다는 것은 아직 독립 검증된 삭제 안전 증명이 아니다.
사용자가 "이거 했는데"라고 말했더라도 승인 명령의 실제 수신·소비는 현장 원장으로 확인해야 한다. 임의 승인 처리 금지.

## P0: 첫 응답 및 기존 승인 소비 확인
1. 사용자에게 먼저 삭제 완료 여부, 기존 승인 상태, 두 폴더 존재 여부를 사실대로 1~3문장으로 답하라. 보고서나 회귀 게이트를 앞세우지 말 것.
2. approval-gate.py와 현행 정본 DB에서 appr-7ec778ec76e6 요청의 waiting/approved/consumed/expired/rejected/withdrawn, 범위 지문, 명령·스크립트 해시, 승인 시각을 읽기 전용으로 확인. 두 경로 모두 원래 승인 범위에 속하는지 검증.
3. 기존 승인이 유효하고 실행 전이면 같은 불변 작업·명령을 사용해 추가 승인 없이 진행. 이미 consumed면 실행 결과와 두 경로의 실제 존재를 먼저 확인, 삭제 완료인 경우 재승인 금지. waiting이면 실제 사용자 승인 입력이 전달됐는지 검증한 후에만 대기; 단지 "지워"라고 했다고 승인된 것으로 위조하지 말라. 기존 요청 번호를 불필요하게 바꾸지 말 것.
4. 삭제 방식 변경(rm→Python→PowerShell)으로 새 요청 번호가 늘어나던 결함을 재현·수정. 승인 게이트를 우회하기 위한 실행 도구 변경이나 DB 직접 쓰기, 거짓 승인, 포괄 예외 등록은 금지.
5. R363의 SYSTEM 관리자 작업 설치는 매우 좁은 remove-shadow-command 한 종류에 한정되어 있다. 이것을 임의 사용자 폴더 전체 삭제용 관리자 통로로 확대하거나 UAC를 회피하지 마라. 현재 두 폴더의 Windows 권한과 승격 필요 여부는 실측으로 확인한다.

## P0: 대량 삭제 전 반드시 안전 검증
1. 각 대상의 canonical 절대경로, 존재, 파일 수·크기, owner, 링크/junction/mountpoint, 경로 탈출 및 다른 실행 중 세션·에이전트가 사용하는지 확인. 승인된 경로 밖 파일을 따라가서 삭제하지 말라.
2. 7개 저장소의 정확한 remote/branch/commit SHA와 tracked 파일 상태를 검증. 특히 로컬 미추적·ignored 파일, 미Push 커밋/브랜치, stash, submodule, Git LFS, 로컬 설정·비밀값, 다른 프로젝트 산출물은 GitHub에 없을 수 있다. GitHub와 같은 소스가 있다는 이유만으로 전체 디렉터리를 안전하다고 가정하지 말라.
3. 로컬 전용 또는 복원이 안 되는 파일이 발견되면 해당 폴더 영구 삭제 중지, 보존 대안을 제시하며 다른 무관한 폴더는 건드리지 말 것. 승인 스냅샷 이후 경로나 내용이 바뀌면 해당 대상 승인 범위 재평가.
4. 안전 조건 통과 및 실제 승인 유효성이 증명되면 정확한 두 대상만 삭제하라. 사용자 작업 중인 다른 파일, 상위·형제 디렉터리, DB/로그/원장/감사 파일 삭제 금지. 사후에 각 Test-Path=False와 다른 경로 보존 실측을 제출하라.

## P0: 한번 승인하면 동일 작업을 끝까지 수행하는 실행 계약
1. 원래 요청에 묶인 대상 두 경로/작업 유형/스냅샷/명령 지문을 불변 operation ID로 취급한다. 명령을 바꾸어서 승인 ID를 새로 만들지 않는다.
2. 승인한 동일 작업은 실행→검증→완료까지 진행. 타임아웃·중단·새 세션에는 기존 승인 범위와 원장 상태를 점검해 안전하게 재개하고, 중복 삭제는 ALREADY_ABSENT로 판정. consumed 단회 승인 토큰을 재활용하거나 복제하는 우회는 금지하며, 승인된 장기 작업의 실행 상태 전이에서만 안전한 재개를 구현한다.
3. 새로운 폴더, 달라진 삭제 범위, 새로운 고위험 작업에는 별도 사전 승인 필요. "GitHub에 있으니 복사본 삭제는 모두 무승인" 같은 포괄적 approval-gate.py 예외는 절대 추가 금지.
4. 비슷한 사용자 승인 작업은 사전에 정확한 대상 경로, 명령, 해시 및 안전 검증 조건을 묶은 제한형 manifest로 등록하고 최초 한 번의 유효한 사용자 승인 후 내부 단계·재시도에서 반복 질문하지 않는 구조를 도입. 승인 없거나 범위 변경되면 차단.
5. 사용자 질문에는 현재 실제 승인/실행 상태를 먼저 즉답. 완료하지 않았으면 완료했다고 말하지 말 것.

## P0: 재현 시험, 교착 원인 조사
- 실제 원장 사건 순서를 확인: 최초 rm 요청, 승인 ID 발급, Python 삭제 차단, 두 번째 요청 발급/취소, 기존 appr-7ec778ec76e6 상태. 로그 없는 부분은 UNKNOWN으로.
- 격리 임시 fixture에서 (a) 두 경로 범위 승인 (b) 동일 요청 중복 (c) 승인 이후 중단/재시작 (d) 이미 삭제됨 (e) 변경된 경로/내용 차단 (f) symlink/junction/경합/잠금 보존 (g) untracked·ignored·미Push 파일 보존 (h) rm/Python/PowerShell 우회 차단 (i) 새 ID 남발 방지 (j) 각각 Test-Path 사후조건을 수정 전 FAIL→수정 후 PASS로 제출.
- 시험에서 실제 3.2GB 운영 대상이나 Windows 시스템 디렉터리를 fixture로 사용 금지. 기존 게이트/원장/Hook 재사용, 새 범용 관리자 서비스/무분별한 반복 회귀 금지.

## 보고와 완료 판정
.ai-collab/reports/R374.md에 2개 폴더별 승인 상태, canonical 경로, remote SHA와 로컬-only 파일 여부, 사전 안전 검사, 실제 실행 코드/시간, 사후 Test-Path, 원장 상태 전이, 소스 수정 SHA, 전후 시험 결과, 필요한 추가 동작을 분리 기재해 GitHub main에 push하라.
- APPROVED+SAFE이면 실삭제·사후 검증까지.
- WAITING이면 기존 ID만 유지, 유효 승인 전에 삭제 절대 금지.
- BLOCKED는 대상별 명확한 사유를 기록하고 사용자 파일을 보존.
- 사용자가 한 번 승인한 동일 작업의 후속 안전 검증·재시도에 반복 승인을 요구하는 결함을 코드로 해결하되, 시스템 안전장치 우회로 해결하지 않는다.

최종 목표: 사용자에게 같은 승인 일을 여러 번 넘기지 않고, 딱 지정된 안전한 작업을 승인된 범위 안에서 끝까지 처리하는 것.
