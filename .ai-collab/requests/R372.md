## 0. 사용자 최신 요구와 현장 사실
사용자 질문: **"왜 갑자기 자동이 안되지... 지침서 또 작성해"**. 핵심은 별도의 지시를 계속 붙여 넣지 않아도 1인 운영 Claude CLI 오케스트레이션이 **새 세션에서 미완료·리뷰·실패를 자동 발견해, 실행 가능한 작업을 스스로 계속 수행**하는 구조다.

실제 Claude CLI 최신 보고:

- 새 세션의 **canva-dev, context7, fetch, github, mermaid** 5 MCP 연결이 각 약 30초 timeout. 대형 회귀 게이트가 돌지 않을 때도 재발 → 단순 게이트 부하 원인으로 확정 금지.
- `verify-fresh-clone` 19:35 실패가 `ensure-state.log`에 남았으나 원인 미조사.
- 최신 코드 커밋 `fadbd05b5186cc5274de92c867b7f61eae546623`, `f0a81e7690132d7458d9c59a2dcc4cd90b496b47`, 보고서 `fb2895a5ae5927dd915449e62ecc6515c43959ac`는 실제 GitHub에서 확인됨. `.ai-collab/reviews/R371.md`는 `changes_requested`, 해당 보고서 `.ai-collab/reports/R371.md`는 `PARTIAL`.

## 1. P0 최우선 — 자동 재개 계약을 실제 코드에 구축
1. **실행 중인 작업 0건**과 **미완료 작업 0건**을 혼동하지 않도록, SessionStart / resume / Supervisor / next-actions / ai-collab poll 정본 경로와 우선순위를 추적한다. 실행중 0건이어도 actionable pending이 존재하면 "모두 끝남" 종료 금지.
2. 세션 시작시 적은 비용의 **복구 체크포인트**를 실행: 로컬 미완료 정본 + GitHub 최신 요청/리뷰/보고/상태 + 승인·차단 상태 + 최근 실패 + 업데이트 변경 알림을 합쳐 중복 제거한 작업 큐를 재구성하라.
3. **ChatGPT 독립 리뷰 `changes_requested` 누락 방지**: 보고서의 reviewed SHA와 원격 리뷰 SHA/상태, 마지막으로 처리한 revision을 비교하여 신규 리뷰가 있으면 세션 시작시 우선 소비하고 원장에 반영한다. 이번 R371 리뷰 6가지 요구가 실제 큐에 들어가는지 증명. 오래된 동일 리뷰를 매 턴 반복 주입하지 않도록 ID/SHA 워터마크.
4. `.claude/state/changelog-new.md`를 읽고 필요 시 `changelog-cache/`의 **실제 새 내용**을 확인, 운영 규칙·명령/훅 동작에 영향하는 변화만 안전하게 반영하라. 존재하지 않는 캐시는 정상 부재로 처리; 변경 내용을 읽지 않고 적용했다고 주장 금지.
5. [claude] 소유의 `READY/IN_PROGRESS/RETRYABLE` 작업은 별도 사용자 반복 질문 없이 실행 가능한 순서대로 **자동 이어서 진행**. 외부 UAC·권한·사용자 판단이 필요한 작업만 `BLOCKED_APPROVAL`로 분리하고 한 번만 요청. `changes_requested`를 단순 보관하는 대신 코드 수정→표적 검증→commit/push→보고→독립 재리뷰 폐루프로 이어라.
6. SessionStart Hook 및 Stop Hook 동작의 시간·토큰·프로세스 부하를 최소화한다. 시작할 때 긴 전체 회귀, 무제한 Agent 생성, 5개 MCP마다 30초 동기 블로킹, 대규모 네트워크 fetch를 방치하지 마라. 제한 시간·중복 방지·백오프·오프라인 큐를 적용하되 중요한 신규 지시를 숨기지 않는다.
7. 사용자가 대화로 질문하면 **최신 상태를 먼저 즉답**하고 긴 작업은 분리한다. 'Queued' 상태의 Claude Code 제품 입력 전송 제한은 실제 수신 이후 처리 지연과 구분해 정직하게 설명한다.

## 2. P0 MCP 5종 연결 실패 — 무부하 재발을 원인까지 조사
1. 각 서버(canva-dev/context7/fetch/github/mermaid) 별 실행 명령, 실제 spawn/exit code, 표준 오류, 타임아웃, 인증·환경 변수 존재 여부(비밀값 출력 금지), cwd·PATH·프록시·네트워크·동시 부팅 경쟁·설정 충돌·서버 메모리·윈도우 프로세스/파일잠금을 분리 수집하라.
2. **서버 자체 실패 / 초기화 핸드셰이크 실패 / 네트워크·인증 실패 / 로컬 훅 부하 / 시작 순서 경합**을 구분하고, 공통 원인이 증명되는지 검사한다. 5개가 동시 timeout이어도 공통 원인으로 성급히 확정하지 마라.
3. 이전 R359 성능 개선에서 MCP 프로세스/등록 개수 조정 및 `--auto` 관련 실제 변경이 원인인지 동일 설정 전후 격리 검증하라. 설정을 일괄 초기화하거나 이미 연결된 다른 MCP를 끊지 마라.
4. 최소 재현(① 단독 기동 ② 5개 동시 기동 ③ 세션 재시작 ④ 게이트 무부하 ⑤ 실패 후 재시도)을 수행. 수정 전 재현 FAIL과 수정 후 연결·정상 도구 호출 PASS, 기동 소요시간/CPU/RAM/프로세스 수의 전후 비교를 제시.
5. 서버가 외부 장애·인증 승인 등에 종속되면 자동 복구 가능한 범위만 재시도·백오프, 장기적으로 실패하면 원장 `DEGRADED` 기록 후 다른 작업 계속. **GitHub MCP 하나 실패했다고 전체 프로젝트 자동 재개를 정지하지 않는다**. 이미 연결된 GitHub API 경로가 있으면 정해진 안전한 대체 경로만 사용하고 비밀/토큰 우회 금지.
6. 현재 실행 성공이 검증되지 않은 MCP 5개를 '연결 문제 해결 완료'라 보고 금지. 각 서버 실제 handshake 및 유의미한 요청 1회 검증 필요.

## 3. P0 verify-fresh-clone 실패 — 실제 실패 로그에서 재현·해결
1. `ensure-state.log`의 2026-11-23 19:35 `verify-fresh-clone` 실패 원문, 실행 스크립트, 호출 환경, exit code, 실패 단계, 대상 SHA를 확인한다.
2. 깨끗한 **임시 격리 clone 또는 안전한 기존 시험 환경**에서 재현한다. 사용자 워킹트리/미추적 파일에 `reset --hard`, `clean -fdx`, 재귀 삭제를 무단 수행하지 마라.
3. 원인(초기화 순서/경로/권한/테스트 의존성/환경설정/설치 누락/공유 state 부재)을 증거로 좁혀 정본을 최소 수정하고 수정 전 FAIL→수정 후 PASS를 기록.
4. 기존 세션 시작 루틴에 fresh-clone 불합격을 자동 탐지·개선 큐에 추가하되, 무조건 대형 게이트 재시작하지 말고 표적 시험부터.
5. 신규 clone에서는 소스만으로 복원 가능한 파일과 로컬 비공개 런타임 상태를 구분. 개인 비밀·승인 DB·감사기록을 원격 push하지 않는다.

## 5. 종단 간 실증 (중요)
1. **새 세션 시뮬레이션**: 실행 중 워커 0 + R371 리뷰 미처리 + C1/A5 등 READY → 자동 읽기, 큐 구성, 표적 작업 시작. 사용자 재지시 없이 이어지는지 증명.
2. GitHub 연결 실패·MCP 5종 타임아웃·fresh-clone 실패가 동시에 발생해도 읽을 수 있는 마지막 정본/캐시 기반으로 안전한 작업 진행, 이후 회복 시 SHA 차분 동기화.
3. 승인 필요 작업은 멈추지만 승인 불필요한 다른 READY 작업은 계속. 잘못된 DONE, 중복 Agent, 사용자 입력 대기 10분, 무한 재전달/불필요한 전체 회귀가 없어야 한다.
4. 작업 끝에서 상태가 PARTIAL이면 세션 종료와 무관하게 다음 실행 가능한 작업이 next-actions 및 정본에 남고, 다음 세션/루프에서 자동 재개되는지 검증.
5. 실제 CLI 세션 재시작을 가능하면 수행하고 전후 로그 시각·요청 수신→작업 시작 시간·MCP 성공 수·fresh-clone 재현과 해결 여부를 기록. 고위험 UI/승인/재부팅은 사용자 동의 없이 수행하지 않는다.
6. 도구/플랫폼이 **세션이 닫힌 후 자동으로 모델을 다시 깨울 수 없다면**, 가능한 것처럼 약속하지 말고 열린 세션의 공식 resume/wait/poll 또는 이미 승인된 스케줄러에 한정해 자동 재개 범위를 증명하라. 단지 next-actions 파일을 저장했다고 자동 실행이라 보고 금지.
