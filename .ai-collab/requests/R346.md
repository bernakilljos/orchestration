# R346 — 안정화 완료 이후 독립 품질 감사·개선·실증·ChatGPT 재검토 폐루프

## 사용자 최신 결정 — 최우선
- **개인 1인용 시스템.** `secrets_vault.py`의 `.env.vault` POSIX 권한 검사, Windows ACL 강화 등 **'비밀정보 저장소 파일 권한 검토·강화' 항목은 이번 범위에서 제외하고 논의/구현/불필요한 재지적도 하지 말 것**. 이것을 무단 보안 완화 허가로 해석하지 않는다. 기존 secret scan, 토큰 마스킹, 금지된 비밀 유출, 사용자 승인 등 기존 보호는 건드리지 않는다.
- 사용자는 현재 작업이 끝날 때까지 새로운 대규모 기능 개발을 원하지 않는다. R334~R345 현행 작업을 완료·안정화한 다음 이 과제를 시작하라. **이 파일을 수신한 것만으로 즉시 코드 수정 금지**.
- 절대 기준은 **속도·성능·품질**, 특정 사례별 **하드코딩 금지**, **사용자 최신 명시 지시 우선**, 실제 공식 레퍼런스와 코드 증거 확인. R335~R345와 중복 구현하지 말 것.
- 지금은 개인용이므로 다중 사용자·SaaS 가정, 대규모 조직용 정책/승인 체계 추가 금지.

## P0 — CI가 실제 실패를 숨기는 문제 (독립 확인된 근거)
`.github/workflows/test-matrix.yml`에는 다음 패턴이 있다: `ruff check ... || true`, `mypy ... || true`, `pytest ... || echo 'No tests found or tests incomplete'`, `validate-plugin-schema.py --strict || true`, `smoke-test.sh || echo ...`. 이로 인해 **해당 단계가 실패해도 GitHub Actions 잡이 성공으로 끝날 수 있음**. 문서의 '테스트 통과' 주장과 CI 실패 감지 능력을 구분해야 한다.
1. GitHub Actions의 실제 트리거/현행 실행 결과/의존성/OS·Python matrix를 조사하고 공식 GitHub Actions·pytest·ruff 문서와 대조.
2. 필수 검사와 참고 검사 분류를 실제 위험/현재 환경에 따라 명확히 결정하고, **핵심 테스트·스키마·보호 검증 실패 시 반드시 작업 실패로 전파**. 애초 의도된 optional 검사만 non-blocking으로 표시하되 실패 로그·원인·범위 감추지 말 것.
3. 테스트 발견 실패/의존성 설치 오류/도구 미설치/테스트 실패를 '테스트 없음'으로 같은 상태 처리하지 말고 구분.
4. 모든 검사에 무조건 전체 회귀를 강요하지 말고 R336의 위험 기반 검증과 연결.
5. **결함 주입/고의 실패 테스트**로 '실패가 CI 실패가 되는지' 확인한 뒤 정상 경로 재검증. 사용자 운영 workflow 건드리기 전 격리·롤백 준비, 의도치 않은 실패 폭주·과금 금지.

## P1 — 장애 복구/데이터 내구성의 실전 증명
1. Supervisor·request ledger·원장 백업·SQLite·inflight lease·GitHub 동기화·worktree·Stop gate의 현재 구현을 먼저 파악하고 R335/R339의 미완 증거를 재활용.
2. 격리된 복제 환경에서 kill/restart(작업 중·원장 저장 중), GitHub 접속 실패, SQLite locking/중간 쓰기, duplicate request/retry, 관련 파일 concurrent write, Stop Hook이 진행 방해 등 **예측 가능한 장애 시나리오**를 실험.
3. Exactly-once 보장 가능성을 섣불리 주장하지 말고 중복 요청 멱등성, 적어도 한 번 재전달 시 부작용, 실행 전후 checksum/증거를 구분.
4. 복구 시간(RTO)·유실/중복 건수·재시도 상한·승인/보안 우회 여부를 실측. 실패한 작업은 PASS가 아니라 BLOCKED/PARTIAL로 기록하고 자동 무한 재시도 금지.
5. 실운영 DB/원장에 장애·삭제 실험 금지, 허가 없이 사용자 CLI 종료·다른 프로세스 종료·실제 Git history 변경 금지.

## P1 — 데이터/학습/규칙 일관성과 완료 품질
1. `orca.db`의 problem_solutions/decisions/활동 로그에 대해 인덱스·자료 품질·verified 플래그·재사용 점수·스테일 데이터·출처·프로젝트 범위 격리와 조회→선별→적용→검증의 실제 효과를 R344와 중복 없이 점검. `ordb.db` 별도 여부는 로컬 확인 전 단정 금지.
2. 여러 SoT·Skill/Command/Hook/Agent 정책에서 사용자 지시와 충돌하는 오래된 지침·무조건 위임·강제 테스트·고정값을 제거/정리하되 개별 프로젝트 예외/보안 보호는 보존.
3. **완료 증거 연결**: 사용자 요구 항목 → 실제 변경 코드/산출물 → 관련 검증 → 최종 완료 상태의 추적성 점검. 하위 하나 완료를 전체 완료로 보고, PARTIAL을 PASS로 꾸미는 경로 금지. 형식상 테스트 PASS와 실제 사용자 요구 충족을 분리.
4. 일반적인 기술 동작은 공식 레퍼런스 실제 본문·현재 설치 버전 대조 후 결정. 실제 원천 자료 없는 환각/하드코딩 금지.

## P2 — 단순 통과가 아닌 실사용 성능·품질
1. `.claude/config/perf-budget.json`은 상태줄 1회, PreToolUse 등 제한된 지표를 계측한다. 전체 관측을 무작정 확장하기 전에 개발 작업 end-to-end 벽시계, 회귀/기다림/Hook/Agent/DB 비용, 실제 오류 재발·재작업률의 계측 가능성을 확인.
2. 대표적인 단순 수정/복합 기능/아키텍처 문서·PPT 작업 등을 개별 샘플로 뽑아 시작→실제 완료까지 단계별 latency·CPU/RAM/토큰·검증 품질 측정. **임시 ChatGPT 협업 5분 poll의 소모를 일반 개발 성능으로 혼동하지 말 것**.
3. 결과가 개선되는 저위험 부분만 수정하고, 효과가 없는 변경은 버림. 병렬화·캐시·성능 기준을 고정 숫자 하나로 하드코딩하지 않고 환경·작업 유형에 맞게 설정/검증된 실측에 기반하여 결정.

## ChatGPT↔Claude CLI 핑퐁(검토→수정→재검토) 종료 규칙
1. Claude CLI는 먼저 **미개발 진단 보고(기준선/확정 결함/미확인/위험도/공식 출처/개선 후보)**를 `.ai-collab/reports/R346.md`에 게시. 이는 구현 승인 자체가 아니다.
2. 보안·민감 권한·운영 파괴 조치는 별도 사용자 승인 필요. 일반 안전한 코드 수정은 사용자가 기존에 명시적으로 승인한 개발·push 범위 내에서 수행 가능하되 **선행 안정화 조건 충족 후**.
3. 코드 수정시 원인별 최소 변경과 실패→성공 회귀 증거, 변경 전후 성능·품질 측정, 공식 레퍼런스·실제 커밋 링크를 단일 증거 보고서에 누적. 보고서를 과거 작업 상태처럼 덮어 거짓 PASS 처리하지 말 것.
4. ChatGPT는 사용자와 합의된 기존 GitHub 검토 루프에서 새로운 보고서/커밋을 실제 읽고 검토하여 누락·반례를 발견하면 **구체적인 보완 지시**를 작성한다. 이미 해결한 항목에 중복 요청 금지.
5. **핑퐁 무한 반복 금지**: 한 건은 근거 확인→최소 수정→재현 가능한 회귀→독립 리뷰까지 완료되면 종료. 근거 없는 스타일 의견/숫자상 점수 상승만을 이유로 수정 반복 금지. 동일 원인 재발 시 코드·테스트에 예방 규칙 기록.
6. ChatGPT가 자동으로 매 순간 감시/즉각 검토한다고 주장하지 말 것. 후속 검토는 기존 연결·정해진 주기/실제 사용자 요청 범위 내에서 수행되며 보지 않은 변경은 미확인으로 둔다.
